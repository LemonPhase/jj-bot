# Development setup

## Prerequisites and start

Use Node.js 24 (minimum 22.12) and npm. Docker is optional: it runs PostgreSQL and the `docker` sandbox driver, or the whole product (see [Docker Compose](#docker-compose)). From the repository root:

```sh
npm ci
JJ_ENABLE_SCRIPTED_MODEL=true npm run dev
```

Open http://127.0.0.1:5173. `npm run dev` starts the API on http://127.0.0.1:3001 with the worker embedded, and the Vite dev server, which proxies `/api` and `/health` to it, following `API_PORT` from the environment or the root `.env`. Stop both with Ctrl+C.

With no settings the API stores everything in embedded PGlite under `.jj-data` and needs no other service. To run bots, configure a model: `JJ_ENABLE_SCRIPTED_MODEL=true` registers the keyless, deterministic scripted test model (`scripted/team`), or put a provider key in `.env` (`cp .env.example .env`), or set `JJ_SECRET_KEY` ([Secrets store](#secrets-store)) and store a key in Settings → Models. Without either, the API stores and serves bots and tasks, bootstrap reports `capabilities.agentExecution: false` and tasks are refused with `MODEL_NOT_CONFIGURED`. Never commit `.env`.

Both sandbox drivers are registered by default. The `docker` driver needs a reachable daemon and its base image, built once with `npm run sandbox:image`; without a daemon it reports unavailable, and when that is so on first boot the seeded default profile is `local` (see [Runtime profiles](architecture.md#runtime-profiles)).

For PostgreSQL, run `docker compose up -d postgres` and set `DATABASE_URL=postgresql://jj:jj_local@localhost:5433/jj_bot`. The compose project `jj-bot` runs PostgreSQL 17 (container `jj-bot-postgres-1`, volume `jj-bot_jj_postgres`) on `127.0.0.1:5433`; `docker compose stop` halts it and `docker compose down` removes the container but keeps the volume.

One process serves everything in production: `npm run build -w @jj/web`, then `npm run start -w @jj/api` serves the built app from `apps/web/dist` on the API port, with client routes falling back to `index.html`.

To run the worker separately, set `DATABASE_URL` and `JJ_EMBED_WORKER=false` for the API and start `npm run dev:worker` (or `npm run start -w @jj/worker`). The worker refuses to start without `DATABASE_URL`, and the API refuses `JJ_EMBED_WORKER=false` on PGlite.

## Docker Compose

`compose.yaml` runs the whole product on one Docker host; the [README quickstart](../README.md#quickstart) has the three commands that start it. `JJ_PORT` changes the published host port. Compose reads `.env` only to fill the variables `compose.yaml` names (provider keys, `JJ_SECRET_KEY` and `JJ_SECRET_KEY_PREVIOUS`, `JJ_DEFAULT_MODEL`, `JJ_ENABLE_SCRIPTED_MODEL`, `API_TOKEN`, the proxy variables, the engine limits, `JJ_PORT`, `JJ_POSTGRES_PORT`, `JJ_DOCKER_NAMESPACE`, `JJ_DOCKER_EGRESS_SUBNET_POOL`, `JJ_DOCKER_SOCKET`, `JJ_LOG_LEVEL`, `JJ_LOG_FORMAT` and the `OTEL_*` variables of [Observability](#observability)); other settings in `.env`, such as `API_HOST`, never reach the container. `docker compose up -d postgres` alone still starts just the database for `npm run dev`.

| Service         | What it is                                                                                                                                                                                                                                                          |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `postgres`      | PostgreSQL 17 with a healthcheck; data in the volume `jj-bot_jj_postgres`.                                                                                                                                                                                          |
| `app`           | The root `Dockerfile`: the API serving the built web app, with the worker embedded, on PostgreSQL. Starts once `postgres` is healthy and `sandbox-image` has exited; its healthcheck (`docker/healthcheck.sh`, every 10 s) is healthy while `/health/ready` is 200. |
| `sandbox-image` | Builds `jj-sandbox:base-1` from `packages/sandbox/images/base` on the host's daemon, where the docker driver looks for it, and exits at once. The app needs the image, not a running container.                                                                     |

- **Image.** A multi-stage build: `npm ci` and the web bundle in one stage, the API's and worker's production dependencies in another, and a Node 24 slim runtime that runs `node --import tsx apps/api/src/index.ts` from `/app`. The code is owned by root and read-only to the app. `.dockerignore` keeps `.env` files, `.npmrc`, keys and certificates, `.jj-data` and `.git` out of the build context at every depth. Behind a TLS-intercepting proxy, pass its CA bundle as the build secret `build_ca` (`docker build --secret id=build_ca,src=ca.pem .`, or `build.secrets` in a compose override); it is never stored in a layer. Compose builds through buildx bake, which refuses a secret file outside the project directory until it is allowed: `docker compose build` with `BUILDX_BAKE_ENTITLEMENTS_FS=0`, or `docker buildx bake --allow fs.read=<dir>`.
- **Authentication.** Inside the container the API listens on `0.0.0.0`, so it always requires a bearer token. `API_TOKEN` sets one, and then no `Open JJ Bot` line is printed: open `<API_PUBLIC_URL>/?token=<API_TOKEN>`. Without it, the API generates a random token (32 bytes, base64url) on its first boot, keeps it in the database (`instance_settings`), reuses it on every later boot, and prints it only in the line `Open JJ Bot: <API_PUBLIC_URL>/?token=<token>`, once per boot, whatever `JJ_LOG_LEVEL` says; `docker compose logs app | grep -o 'Open JJ Bot: [^"]*'` shows it without the rest of the JSON line. Every other line redacts it. Treat the logs as secret; `docker compose down -v` discards the token with the data, and deleting the `api_token` row of `instance_settings` makes the next boot generate a new one. The port is published on the host's loopback only; publish it further only behind HTTPS, so the token never crosses a network in the clear.
- **Sandboxes.** Only the `docker` driver is registered (`JJ_SANDBOX_DRIVERS=docker`), so the default profile is the isolated docker sandbox. Never enable `local` in the container: its commands would run next to the model keys and the Docker socket. Sandboxes are sibling containers on the host's daemon, on Docker's default bridge network rather than the compose network (with network `open`; `allowlist` sandboxes get a network of their own), so they cannot reach the app or PostgreSQL by service name or container address; without the token they could not use the API even where they reach it (on Docker Desktop, through `host.docker.internal`). Their namespace (`JJ_DOCKER_NAMESPACE`) defaults to the compose project name, `jj-bot`, so separate projects on one daemon never reap each other's sandboxes. The one-worker-per-namespace constraint below applies: the compose app is that namespace's worker.
- **The Docker socket.** The host's socket is mounted at `/var/run/docker.sock` (`JJ_DOCKER_SOCKET` picks another host path, such as a rootless daemon's). It is root-equivalent on the host: whoever controls the app container controls the host. The driver never passes it into a sandbox, never starts privileged containers and never bind-mounts host paths ([Sandbox boundary](architecture.md#sandbox-boundary)). The mount pins the socket as it was when the container started: if the daemon restarts underneath a running app (with `live-restore`), the old socket is gone, the driver reports unavailable and the app turns unhealthy until `docker compose restart app`.
- **No root.** The entrypoint (`docker/entrypoint.sh`) starts as root only to read the group id of the socket (following a symlink), which differs per host. It adds that group to the user `jj` (uid 10001) only when the group can read and write the socket, then drops to `jj` with `setpriv` and `no_new_privs`, emptying the capability bounding set when it may; the app holds no capabilities. A socket its group cannot use is reported in the log, and the driver then reports unavailable: make the socket group-accessible, or reach the daemon through a socket proxy by setting `DOCKER_HOST` in a compose override (plain `tcp://` beyond loopback also needs `JJ_DOCKER_ALLOW_INSECURE_TCP=true`). An image started with `--user` skips the switch, so give that user the socket's group with `group_add`. The container also runs with a read-only root filesystem, a `/tmp` tmpfs, `no-new-privileges` and every capability dropped except `SETUID` and `SETGID` (the entrypoint) and `KILL` (init forwarding stop signals).
- **Proxy.** `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` pass through for model calls. `127.0.0.1` inside the container is the container itself; a proxy on the host is `host.docker.internal`.
- **Restarts.** `docker compose restart app` or `stop` sends SIGTERM and allows 30 s, more than the API's own 20 s shutdown limit, so running sessions are handed back and resume from their last completed turn when the app starts again; a command cut short is reported as interrupted, never re-run, and the task workspace keeps its files.
- **Data.** `docker compose down -v` removes the PostgreSQL volume, but not the sandboxes' task workspaces, which are Docker volumes named `<namespace>-task-<taskId>` and labelled `jj.sandbox.namespace=<namespace>`. With the default namespace, `docker volume ls -q --filter label=jj.sandbox.namespace=jj-bot | xargs -r docker volume rm` removes them. [Backup, restore and upgrades](#backup-restore-and-upgrades) covers both.

## Backup, restore and upgrades

A JJ Bot install's state is its database and its task workspaces. The database holds every record: bots, profiles, memory, conversations, tasks with their sessions, transcripts, messages and events, the stored artifacts (their bytes are in `artifacts.content`), usage, the stored secrets as ciphertext and the generated API token. Task workspaces are the docker driver's volumes (`<namespace>-task-<taskId>`); ephemeral workspaces live only as long as their sandbox and are not state. Neither holds `JJ_SECRET_KEY`, and neither should: keep the key, like the rest of `.env`, apart from every backup.

### The compose stack

`scripts/backup.sh [DIR]` backs up the running stack into `DIR`, relative to the current directory (default `backups/<project>-<UTC time>` in the repository, which `.gitignore` and `.dockerignore` exclude). It needs only Docker: from the repository root it runs `docker compose`, so `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME` and `.env` apply as they do to the stack, and the stack must be up.

- `database.dump` is `pg_dump --format=custom` of the whole database: one consistent snapshot, taken while the app keeps working.
- `volumes/<volume>.tar` and `.labels` hold each task workspace in the namespace and the driver's labels on it, copied by a throwaway container (the `JJ_BACKUP_IMAGE`, default `jj-sandbox:base-1`) that mounts the volume read-only, without network or capabilities beyond reading. A command writing a file during the copy can leave that one file partial; for a quiet copy, back up between tasks. A workspace that is gone by the time it is copied (a sandbox released it) is skipped, and the script says so.
- `check.json` and `check.env` are the data check (below) just before the dump: this build's version, contract version and migrations, the database's migration level and its record counts. `manifest.json` gathers them with the time, the compose project, the namespace, the checkout's commit, the PostgreSQL versions and the workspaces, and `SHA256SUMS` covers every other file.
- A backup is as secret as the server: the dump holds the generated API token and every conversation. The script creates it readable by its owner only.

`scripts/restore.sh [--force] DIR` restores one into the stack of the checkout it runs in. Restoring a backup means trusting it, as much as handing it the database: `pg_restore` runs its SQL as the database's superuser. Checksums detect damage, not tampering; a backup must come from a trusted source.

1. Before it changes anything, it checks the backup and the stack, and refuses with `Nothing was changed` when one does not hold:
   - the checksums: every line of `SHA256SUMS` is a SHA-256 and a backup file, and they cover every file it reads;
   - every workspace archive is one the manifest lists, named `<namespace>-task-<key>` or `<namespace>-bot-<key>` in the backup's namespace, with exactly the docker driver's labels;
   - no volume of a workspace's name exists outside this stack's namespace;
   - this build ships the migration the backup's database is at (it never migrates backwards);
   - this stack's PostgreSQL is the backup's major version or a later one (one archive format serves several majors, so a newer major's dump can read fine and still fail partway), and its `pg_restore` reads the dump;
   - no container outside the namespace's sandboxes uses one of its workspace volumes, which `--force` removes.
2. It refuses a stack that holds data (a database JJ Bot has opened, a workspace volume in its namespace, or a running app), naming what it found, unless `--force` is given. `--force` stops the app, removes the namespace's sandboxes and workspace volumes and recreates the database, so the backup replaces everything. A new host restores with `docker compose build`, `scripts/restore.sh DIR`, then `docker compose up -d --wait`.
3. It restores the database with `pg_restore --single-transaction`, then each workspace into a new volume with the driver's labels, under this stack's namespace, so the docker driver mounts it for its task again. It never writes into a volume that already exists.
4. It runs the restore check and compares the record counts with the backup's. The app stays stopped: `docker compose up -d --wait` starts it, and it migrates an older schema at boot. Tasks that were running when the backup was taken resume as after a crash, from their last completed turn; a command cut short is reported as interrupted, never re-run.

It exits 1 when the backup is damaged or refused, the stack refuses it, or the restore check fails: a restored database newer than this build is named as such, and a check that cannot read the database is reported apart.

`scripts/backup-restore.test.ts` runs both scripts against a stand-in docker CLI (`scripts/fake-docker.sh`) for the paths a stack seldom takes: no workspace, a workspace that vanishes, a damaged backup or one holding files its manifest and the driver's naming do not account for, a dump, PostgreSQL version or migration the stack cannot take, a workspace volume in use, and a failing check. CI's Compose stack job runs them on the real stack.

### The data check

`npm run data:check` (in the compose stack, `docker compose run --rm --no-deps app node --import tsx apps/api/src/data-check.ts`) reads the configured database without migrating or writing anything and reports:

- **Schema:** `empty` (JJ Bot never opened it), `behind` (an older release's; the server applies the newer migrations when it starts), `current`, or `newer` (written by a newer version, which this build refuses to start on; exit code 1).
- **Records:** bots, tasks, artifacts and their bytes.
- **Secrets:** how many are stored, and by name the ones the configured `JJ_SECRET_KEY` (with `JJ_SECRET_KEY_PREVIOUS`) cannot read. A backup restored under another key, or none, keeps those rows unreadable ([Secrets store](#secrets-store)): set the key they were stored with, or move them to a new one by keeping the old key in `JJ_SECRET_KEY_PREVIOUS`, or store them again in Settings. Also how many replaced or removed values are kept for redaction, and how many of those the key cannot read: those are no longer redacted, until the key that sealed them is set.

`--json` and `--env` (`key=value` lines) print the same for scripts.

### PGlite

A PGlite data directory (`JJ_DATABASE_PATH`, default `.jj-data`) is the whole database. Stop the server first: the directory is locked to the running process and a copy taken while it writes may not open. Copy the directory (`cp -a .jj-data <backup>`), and the `local` driver's workspaces under `JJ_SANDBOX_ROOT` if they matter; restore by copying them back while the server is stopped. A `jj-db.lock` left in a copy names a process that is gone, so the next open takes it over. `JJ_DATABASE_PATH=<backup> npm run data:check` checks a copy.

### Upgrades

Migrations are forward-only: there is no downgrade.

1. Back up: `scripts/backup.sh` (with PGlite, the directory copy above), and keep `JJ_SECRET_KEY`.
2. Update the checkout to the new release and run `docker compose up -d --build --wait`. The app applies the new migrations when it opens the database, all in one transaction; PostgreSQL openers serialize on an advisory lock, so a separate worker booting at once is safe.
3. Check `docker compose logs app` and `/health/ready`, whose `migrations` check reports none pending.

To go back, restore the backup taken before the upgrade with the old release (`scripts/restore.sh --force`): a build older than its database refuses to start, with `This database was written by a newer version of JJ Bot: …` naming the newest migration it knows, before it applies or changes anything. A PostgreSQL major version is upgraded by the same route: back up, change the `postgres` image, `docker compose down -v`, then `scripts/restore.sh --force`, since the workspace volumes outlive `down -v` and the backup replaces them.

The upgrade tests start from the previous release's schema with data its build wrote (`PREVIOUS_RELEASE` in `packages/db/src/testing.ts`, its fixture in `packages/db/fixtures`), open it through the boot path, and check that every record keeps its values, the current schema reads every table, and the server serves it and continues its task. Each release moves `PREVIOUS_RELEASE` forward with a fixture its own build writes.

## Workspace ownership

| Directory            | Responsibility                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------- |
| `apps/web`           | React/Vite workspace: bot chat, task chat, execution view, steering and stop, settings; its browser suite      |
| `apps/api`           | Hono HTTP and SSE layer over the engine, health and readiness, serving the built web app; the composition root |
| `apps/worker`        | Standalone job loop on the API's wiring, for PostgreSQL deployments that do not embed the worker               |
| `packages/contracts` | Canonical Zod schemas and types: the HTTP and SSE contract                                                     |
| `packages/backend`   | The engine: bots, profiles, tasks, messages, chat, artifacts and views, and the worker that runs sessions      |
| `packages/runtime`   | The pi agent runtime: model registry, session executor, chat responder and the scripted test model             |
| `packages/sandbox`   | Sandbox driver contract, the `local` and `docker` drivers and the shared driver conformance suite              |
| `packages/db`        | Drizzle schema and migrations, per-task sequences, job queue and LISTEN/NOTIFY bus on PostgreSQL or PGlite     |

Internal packages export TypeScript source. The API and worker run with `tsx`; `build` typechecks all packages and produces the web bundle.

The API's composition root is `apps/api/src/server.ts` (`startServer`). It configures the outbound proxy, opens the database (applying migrations), registers the sandbox drivers, builds the model registry, executor and chat responder and the engine, listens, and then starts the embedded worker, so a port clash fails before any run is claimed. `createApp({ engine, config })` in `apps/api/src/app.ts` is the HTTP app alone, so tests drive it with `app.request`. `apps/api/src/wiring.ts` (`openServices`) is shared with `apps/worker`.

### Web app structure

`apps/web/src` keeps screens in feature folders (`features/shell`, `bots`, `tasks`, `office`, `studio`, `settings`), the design-system kit in `components/ui` and `components/sprite`, pure helpers in `lib`, and the backend seam in `api` (`JJApi`) with workspace state in `state`. Screens are addressed by URL hash, so every view is linkable and survives a reload: `#/bots/:botId`, `#/tasks/:taskId`, `#/studio` (new bot) or `#/studio/:botId`, and `#/settings`. `features/shell/router.ts` parses and formats them and `useRoute()`/`navigate()` bind them to the window; a list route without an id opens the first item. Only the Bots screen is in the entry chunk: the Tasks, Studio and Settings screens, the 3D office (Three.js) and the demo data are chunks of their own, loaded when first used. A deep link or reload starts loading its screen's chunk at boot, while the API is probed and the workspace loads, and the screen shows a spinner naming it ("Loading Settings…") until the chunk arrives; a screen whose chunk fails to load says so with a reload instead of blanking the app. The web app runs on built-in demo data, its mode badge reading "Demo data" with the reason in its tooltip, only when no JJ Bot backend is there at all (`/api/bootstrap` answers 404 or with the app's own `index.html`, as a static host does, or in scaffold mode), or with `?demo`, which forces it. When the API is unreachable (offline, or a 5xx), asks for a token, is redirected (a sign-in page), answers anything else or speaks another contract major version, the app says so, naming the HTTP status, with a reload, and never shows demo data in place of the workspace. The dev-only kit gallery is at `?gallery=1`.

The app fills the viewport at every width and only its panes scroll, never the page. Below 760px (`NARROW_QUERY` in `lib/media.ts`, the stylesheets' `max-width: 759px`) it is laid out for phones from 360px wide: a top bar with the menu button and the mode badge replaces the sidebar, which opens from the menu as a modal drawer; a task's chat fills the first screen with the Progress | Graph | Office panel below it; no screen or pane scrolls sideways except the ones meant to (Settings' section tabs, wide tables, the graph); every control is at least 44×44 px; and text fields use 16px type, so phones do not zoom in on them. The 3D office is offered only on wider screens with WebGL; otherwise the 2D office shows, and the switch says why 3D is off.

### Installable web app

The built app is installable: `public/manifest.webmanifest`, its icons and the service worker `public/sw.js`. The icons are drawn from the brand mark in `public/favicon.svg` by `npm run icons -w @jj/web`, and `icons.test.ts` fails when a committed PNG no longer matches. `src/lib/serviceWorker.ts` registers the worker after the page loads, in production builds only, so `npm run dev` and the unit tests never run it. It caches the app shell and nothing else:

- It never handles `/api/*`, `/health*`, other origins or any method but GET: API answers, the event streams and the token go to the network as without a service worker, and nothing from them is stored.
- Page loads are network first: the server's answer whenever it answers, so a deploy shows on the next load and nobody is left on a stale shell. Only the app's own `index.html` (a 200, not redirected, loading a hashed entry script) is stored, without the address it came from (so no `?token=`), and it is served only when the network fails or the server answers with a 5xx (down behind a proxy), so the app still opens and says that the API cannot be reached. A maintenance or login page is shown but never stored.
- Vite's content-hashed files (`/assets/<name>-<hash>.<ext>`) are served from the cache once stored, else fetched, and stored only when the answer is really that file: a 200, not redirected, of the type a known extension calls for (never a web page) and, for scripts, styles and JSON, with a body that is not markup. Other files under `/assets/`, unknown extensions and the demo data's chunk are never stored. A shell that changed is stored once the assets it loads first are, so the stored shell always has them; then stored assets that neither the stored shell loads nor the server still has are dropped. Other screens' chunks are stored when first used.
- Recovery: a release that changes `CACHE` in `sw.js` makes every browser drop its other `jj-shell-*` caches when the new worker activates, which it does at once (`skipWaiting`, `clients.claim`). To retire the worker altogether, ship a `sw.js` that unregisters itself and deletes those caches.

## Configuration

Settings are environment variables, read from `.env` at the repository root by the dev and start scripts. Relative paths resolve against the repository root. A setting that cannot work stops the process at startup with a message naming it.

| Variable                                | Purpose                                                                                                                                                                                                            |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `API_HOST`                              | Listener address, default `127.0.0.1`. Beyond loopback the API always requires a token: `API_TOKEN`, else one it generates on first boot and keeps in the database.                                                |
| `API_PORT`                              | Listener port, default `3001`; `0` picks a free one.                                                                                                                                                               |
| `API_TOKEN`                             | Bearer token required on `/api/*` when set. The web app reads it once from `?token=`, keeps it in localStorage and removes it from the address bar.                                                                |
| `API_PUBLIC_URL`                        | Where users open the app, for the `Open JJ Bot` line that carries a generated token; default `http://127.0.0.1:<API_PORT>`.                                                                                        |
| `API_ALLOWED_HOSTS`                     | Without `API_TOKEN`, `Host` values besides loopback that `/api/*` answers, comma-separated: a hostname (any port) or `host:port`. For reverse proxies.                                                             |
| `DATABASE_URL`                          | PostgreSQL connection string. When set, the API and worker use PostgreSQL.                                                                                                                                         |
| `JJ_DATABASE_PATH`                      | PGlite data directory when `DATABASE_URL` is unset, default `.jj-data`; `memory://` keeps nothing (bootstrap reports no persistence).                                                                              |
| `JJ_EMBED_WORKER`                       | `true` (default) runs the job loop in the API; `false` leaves it to `apps/worker` and needs PostgreSQL.                                                                                                            |
| `JJ_ENABLE_SCRIPTED_MODEL`              | `true` registers the keyless scripted test model `scripted/team`, and `scripted/team-priced` at a fictional price for spend caps. The web app labels it "Scripted model".                                          |
| Provider keys                           | One variable per provider, such as `OPENAI_API_KEY` or `ANTHROPIC_API_KEY`; `GET /api/models` lists every provider with its `envVars`. A variable takes precedence over a key stored in settings.                  |
| `JJ_SECRET_KEY`                         | Master key of the secrets store: base64 of at least 32 random bytes (`openssl rand -base64 32`). Unset: nothing can be stored in settings. See [Secrets store](#secrets-store).                                    |
| `JJ_SECRET_KEY_PREVIOUS`                | Earlier master keys, comma-separated, during a rotation: stored values they sealed are still read, and sealed again under `JJ_SECRET_KEY` at boot.                                                                 |
| `JJ_DEFAULT_MODEL`                      | `provider/model` for bots without a model, when the catalog lists it and its provider is configured; otherwise a cheap model of the first configured provider. A set value left unused is a boot warning.          |
| `JJ_CONCURRENCY`                        | Jobs (session runs and chat replies) one worker runs at once, default `4`.                                                                                                                                         |
| `JJ_MAX_SESSIONS_PER_TASK`              | Sessions a task may create, default `16`.                                                                                                                                                                          |
| `JJ_MAX_DELEGATION_DEPTH`               | Delegation depth below the coordinator, default `3`.                                                                                                                                                               |
| `JJ_TASKS_PER_BOT_PER_HOUR`             | Tasks a bot may create from direct chat per hour, default `10`.                                                                                                                                                    |
| `JJ_MAX_USD_PER_DAY`                    | What the whole server may spend on priced model calls in any 24 hours, in US dollars; unset (default) for no instance cap. Task and bot caps are in runtime profiles.                                              |
| `JJ_OUTPUT_CAP_BYTES`                   | Tool output kept in events, default and maximum 65536; larger output is stored as an artifact.                                                                                                                     |
| `JJ_MAX_VERIFICATION_ATTEMPTS`          | Verification gate runs one coordinator run may make on a task with a plan, default `3`; after the last failed one the task waits for the user.                                                                     |
| `JJ_EPHEMERAL_IDLE_MINUTES`             | Minutes an idle ephemeral workspace is kept while its task is open, default `360`; its release discards the files.                                                                                                 |
| `JJ_MAX_HELD_SANDBOXES`                 | Sandboxes one worker holds at once, default `32`; over it the least recently used idle one is released.                                                                                                            |
| `JJ_SANDBOX_DRIVERS`                    | Drivers to register, comma-separated from `docker` and `local`, default both. `docker` stays registered without a daemon and reports unavailable.                                                                  |
| `JJ_SANDBOX_ROOT`                       | Workspace root of the `local` driver, default `<os.tmpdir()>/jj-sandbox`; the OS may clear it, so point it somewhere durable. The operator clears it.                                                              |
| `JJ_DOCKER_NAMESPACE`                   | Container and volume name prefix of the `docker` driver, default `jj-sandbox`.                                                                                                                                     |
| `DOCKER_HOST`                           | Docker Engine API address, default `/var/run/docker.sock`. Plain-HTTP `tcp://` beyond loopback needs `JJ_DOCKER_ALLOW_INSECURE_TCP`.                                                                               |
| `JJ_DOCKER_ALLOW_INSECURE_TCP`          | `true` lets the `docker` driver use plain-HTTP `tcp://` to a host that is not loopback, such as a socket proxy's service name. Default `false`.                                                                    |
| `JJ_DOCKER_EGRESS_SUBNET_POOL`          | Private IPv4 range (`a.b.c.d/n`, n 8–28, in 10/8, 172.16/12, 192.168/16 or 100.64/10) whose /28s the `docker` driver's `allowlist` networks use; default `10.213.0.0/16`. Keep it clear of Docker's default pools. |
| `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY` | Outbound proxy for model provider calls (either case; lowercase wins). A proxy's CA goes in `NODE_EXTRA_CA_CERTS`.                                                                                                 |
| `JJ_LOG_LEVEL`                          | `debug`, `info` (default), `warn` or `error`: the lowest level logged. See [Observability](#observability).                                                                                                        |
| `JJ_LOG_FORMAT`                         | `json` (default): one JSON object per line; `pretty`: one readable line, for a terminal.                                                                                                                           |
| `OTEL_EXPORTER_OTLP_ENDPOINT`           | An OTLP/HTTP collector (`http://collector:4318`): spans go to `<endpoint>/v1/traces`. Unset (default), no trace SDK is loaded.                                                                                     |
| `OTEL_EXPORTER_OTLP_HEADERS`            | Headers for the collector, `key=value` comma-separated, such as an API key; `OTEL_EXPORTER_OTLP_TRACES_HEADERS` adds to them. Both are redacted like the other secrets.                                            |
| `JJ_POSTGRES_PORT`                      | Host port of the compose PostgreSQL service (loopback), default `5433`.                                                                                                                                            |
| `JJ_PORT`                               | Host port of the compose app (loopback), default `3001`.                                                                                                                                                           |
| `JJ_DOCKER_SOCKET`                      | Host path of the Docker socket compose mounts into the app, default `/var/run/docker.sock`.                                                                                                                        |

### Secrets store

Provider keys and sandbox secrets entered in settings are encrypted with `JJ_SECRET_KEY` ([Secrets store](architecture.md#secrets-store)). To turn the store on, run `echo "JJ_SECRET_KEY=$(openssl rand -base64 32)" >> .env` at the repository root and restart the server (compose reads it from the same `.env`). Every process that opens the database, a separate worker included, needs the same key.

- **Back it up apart from the database.** Database backups hold each value only as ciphertext, readable only in its last four characters and its length; without the key a backup restores the names but no value. Never store the key next to a database dump. The restore check names every stored value the configured key cannot read, and counts the replaced or removed ones it can no longer redact ([The data check](#the-data-check)).
- **Rotation.** Generate a new key, set it as `JJ_SECRET_KEY` and move the old one to `JJ_SECRET_KEY_PREVIOUS`, then restart every process. The server seals every stored value again under the new key at boot, retired ones included, and logs how many. Once Settings shows no unreadable secret, remove `JJ_SECRET_KEY_PREVIOUS` and restart. Rotation protects values against the old key leaking later; a value that leaked with its key must be revoked where it was issued.
- **Loss.** A server started with another key, or with none, keeps the stored rows but cannot read them: it names them in a warning at boot, Settings lists them as unreadable, their providers are not configured, and a task whose sandbox is granted one fails visibly. Restore the key, or store each value again (or remove it) in Settings.
- **Replaced and removed values.** Replacing or removing a value in Settings retires the old one: the server keeps it encrypted, in `retired_secrets`, for 90 days (at most the 10 most recent of each name) and redacts it from task history, since a task may still print it from a file it wrote. It is never injected or shown, and while it is kept a retired model key cannot become a sandbox secret. To drop retired values sooner, delete their rows (`DELETE FROM retired_secrets`); they are then no longer redacted.
- **Local driver.** On `local`, commands run as the server's user and can read its environment, `JJ_SECRET_KEY` included, and its database, and so every stored value. Use `docker` for anything granted a secret.

Schema: opening the database applies the SQL migrations in `packages/db/migrations`, so there is no separate migration step; processes opening one PostgreSQL database at once serialize on an advisory lock. To change the schema, edit `packages/db/src/schema.ts`, run `npm run db:generate -w @jj/db` and commit the generated migration. Migrations are forward-only: never edit one that has been applied, and never write one that older data cannot pass through (the upgrade tests load the previous release's data). A database with migrations newer than the build is refused at boot ([Upgrades](#upgrades)). The store's contract is in `packages/db/README.md`.

- **Errors.** Every non-2xx JSON answer is `{ error: { code, message, details? } }` with a contract code and its status (`VALIDATION_FAILED` 400, `UNAUTHORIZED` 401, `NOT_FOUND` 404, `CONFLICT` and the other refusals 409, `MODEL_NOT_CONFIGURED`, `PROFILE_UNSUPPORTED`, `VERIFICATION_UNAVAILABLE` and `MCP_UNAVAILABLE` 422, `RATE_LIMITED` 429). A body that is not JSON is `VALIDATION_FAILED`, one over 1 MiB is `VALIDATION_FAILED` with 413, an unknown route is `NOT_FOUND`. Anything unexpected is `500 INTERNAL` with no detail; the stack goes to the server log.
- **Browser protection.** Every `/api/*` request with `Sec-Fetch-Site: cross-site` is refused with 403. Without `API_TOKEN`, only loopback `Host` values (`localhost`, `127.0.0.1`, `[::1]`, any port) and `API_ALLOWED_HOSTS` are answered; any other `Host`, such as a DNS-rebinding page's own name, gets 403. POST, PUT and PATCH need `Content-Type: application/json` (415 otherwise), so a cross-origin write always needs a CORS preflight, and the API sends no CORS headers. The Vite dev proxy keeps the browser's `Host` (`127.0.0.1:5173`), so it passes. With a token, configured or generated, the bearer check replaces the `Host` check.
- **Validation.** The engine parses every request body with its contract schema. Path ids, `after`, `limit` and `Last-Event-ID` are checked in the API.
- **Task stream.** One frame per event: `id:` the sequence, `event:` the type, `data:` the event JSON. It replays events after `Last-Event-ID`, else after `?after=`, else from the start, then streams new ones; each event is sent once, in order. An unknown task answers 404 before the stream opens. The stream stays open after the task finishes, since a message can continue it.
- **Workspace stream.** One frame per hint, `event:` its type and `data:` the hint JSON, without ids: it is not resumable, so clients refetch on (re)connect.
- **Both streams** send `: heartbeat` comments every 15 s, carry `Cache-Control: no-cache` and `X-Accel-Buffering: no`, close their database subscription when the client disconnects, and end on shutdown, even when the client has stopped reading. `HEAD` gets the stream headers and opens nothing. The workspace stream subscribes before its response starts, so no hint falls between subscribing and the client seeing the stream open.
- **Artifacts** download as `Content-Disposition: attachment` with the artifact's content type, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`, so agent-written files never run as the app's pages.
- **Health** is unauthenticated and reports states, counts and reasons only; see [Observability](#observability).
- **Static files.** When `apps/web/dist` exists, other paths serve its files, and page routes without a file extension fall back to `index.html`. They never answer `/api`, `/health` or `/metrics`. Hashed `/assets/*` are cached for a year as immutable; every other file (`index.html`, `sw.js`, the manifest and icons) is `no-cache`.

Task execution is owned by the worker, not by an HTTP request or an open stream: closing the browser does not stop a task. Access control is one shared bearer token (configured, or generated whenever the API listens beyond loopback) plus the browser protection above; there is no per-user identity. Publish the API beyond loopback only behind HTTPS, so the token never crosses a network in the clear.

## Observability

Logs, traces and metrics carry no secret and, in traces and metrics, no task content ([Observability](architecture.md#observability)). The standalone worker logs and traces like the API; it serves no `/metrics`, so the API's `/metrics` reports a separate worker's queue but not its runs.

### Logs

- **Format.** One JSON object per line, `{"time", "level", "msg", …}`, with debug and info on stdout and warn and error on stderr. `JJ_LOG_FORMAT=pretty` writes `<time> <LEVEL> <message> key=value …` instead, for a terminal, and is what `npm run dev` uses (`apps/api/dev.env`, which the root `.env` and the shell override); `JJ_LOG_LEVEL` drops the levels below it (default `info`).
- **Ids.** A line written while a request, a job or a run is handled carries the ids it has: `requestId`, `jobId`, `botId`, `taskId`, `sessionId` and `runId`. A request's id is a well-formed `X-Request-Id` from a proxy in front (letters, digits, `._:-`, at most 64), else a new `req_…`; it is answered in `X-Request-Id`.
- **Request lines.** Each request is logged when its response starts, as `<METHOD> <path> <status>` with `method`, `path` (never the query, which can carry `?token=`), `status` and `durationMs`: a health probe at debug whatever it answers, a 5xx at warn, a refusal (4xx) or a change (any method besides `GET`, `HEAD` and `OPTIONS`) at info, and a read that succeeded, a scrape included, at debug. An unexpected failure also logs its stack at error.
- **Runs.** `Session run started` and `Session run finished` (with `outcome`, `durationMs`, `modelCalls`, `toolCalls`, `inputTokens`, `outputTokens`, `costUsd`), `Chat reply started` and `Chat reply finished` at info; `Model call finished` and `Tool call finished` at debug. An outcome is the executor's (`ended`, `idle`, `held`, `budget`, `aborted`, `error`), a reply's `ok` or `error`, or how the worker stopped it (`cancelled`, `handed_back`, `lease_lost`, `crashed`).
- **Never logged.** Every line, its message, its fields and their names, goes through the engine's redactor: provider keys, `API_TOKEN` and the generated token, `JJ_SECRET_KEY` and the previous keys, the database password in a URL, the values of `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_EXPORTER_OTLP_TRACES_HEADERS`, every value of the secrets store and the retired ones it keeps, and the values of the sandboxes the worker holds. A value stored in Settings is redacted from the next line on. The `Open JJ Bot` line is the one exception, for the generated token alone, and it is printed whatever the level. Run and call lines carry no prompt, brief, message, tool argument, tool output or model text; error messages are logged as raised, redacted. An error nothing caught is logged the same way, at error, and the process exits 1. Lines logged before the engine opens (a setting that cannot work, a database that cannot be opened) are not redacted, and name settings, never their values; the trace export line masks the endpoint's user, password and query values.

### Traces

Set `OTEL_EXPORTER_OTLP_ENDPOINT` to export OpenTelemetry spans over OTLP/HTTP (JSON) to `<endpoint>/v1/traces`, or to `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` when that is set too, with `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_EXPORTER_OTLP_TRACES_HEADERS`. The service name is `jj-api` or `jj-worker` unless `OTEL_SERVICE_NAME` or `OTEL_RESOURCE_ATTRIBUTES` names another. Unset, the SDK and the exporter are never loaded. Spans are batched and flushed at shutdown. An export that fails, or takes more than 5 s, is logged as a warning and its spans are dropped, so a collector that refuses or does not answer never delays a shutdown by more than that, nor fails it.

| Span                 | Parent               | Attributes besides `jj.outcome`                                                                                                   |
| -------------------- | -------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `jj.session.run`     | none                 | `jj.task.id`, `jj.session.id`, `jj.run.id`, `jj.bot.id`, `jj.job.id`, `jj.session.role`, `jj.run.reason`, `jj.run.number`, totals |
| `jj.chat.reply`      | none                 | `jj.bot.id`, `jj.job.id`, `jj.task.id` (a task update), `jj.error.code`, totals                                                   |
| `jj.model.turn`      | the run or the reply | `gen_ai.provider.name`, `gen_ai.request.model`, token counts, `jj.cost_usd`, `jj.unpriced_calls`, `jj.stop_reason`                |
| `jj.tool.call`       | the run or the reply | `gen_ai.tool.name` (`other` for a name the run did not declare), `gen_ai.tool.call.id`, `jj.tool.exit_code`                       |
| `jj.sandbox.acquire` | the run              | `jj.sandbox.driver`, `jj.task.id`, `jj.session.id`                                                                                |

Totals are `jj.model_calls`, `jj.tool_calls`, the `gen_ai.usage.*` token counts and `jj.cost_usd`. A turn or call still open when its run stops ends `interrupted`. `SPAN_ATTRIBUTES` in `packages/backend/src/observability/tracing.ts` is the whole list: no attribute holds a prompt, a tool's arguments or output, or model text.

### Metrics

`GET /metrics` answers the Prometheus text format, behind the same browser protection and bearer token as `/api` (a scrape config sets `authorization: { credentials: <token> }`). It reports the API process's engine and its embedded worker, and the process's own CPU, memory, event loop and GC metrics.

| Metric                                | Labels                      | What                                                     |
| ------------------------------------- | --------------------------- | -------------------------------------------------------- |
| `jj_queue_depth`                      | `kind`                      | jobs queued and due, of every worker, read at the scrape |
| `jj_worker_active_jobs`               |                             | jobs this process's worker runs                          |
| `jj_queue_claim_latency_seconds`      | `kind`                      | from a job becoming due to its first claim               |
| `jj_session_run_duration_seconds`     | `role`, `outcome`           | session runs                                             |
| `jj_tool_call_duration_seconds`       | `tool`, `outcome`           | tool calls of runs and chat replies                      |
| `jj_model_calls_total`                | `provider`, `model`         | model calls, compaction summaries included               |

### Health

- **`GET /health/live`** (and `GET /health`, the same) is 200 while the process answers; it checks nothing else.
- **`GET /health/ready`** is 200 with `status: "ready"`, else 503 with `not_ready`, and a `reason` per check: `database` (a query answers), `migrations` (applied and expected counts; none pending and none newer than this build), `worker` and `drivers` (the available and unavailable driver ids; at least one available). With the worker embedded, `worker` is the job loop's last claim pass, within 30 s (`lastPollAt`, `activeJobs`). With `JJ_EMBED_WORKER=false` it is fresh when some worker, embedded in another API or standalone, wrote its row in `worker_heartbeats` within 30 s (`workers`, `lastSeenSecondsAgo`); every polling worker on PostgreSQL writes it at most every 5 s with the database clock and deletes it on a graceful stop, so a crashed one goes stale (on PGlite no other process could read it, so none is written). A check that does not answer within 3 s fails with `no answer within 3000 ms`.
- Both are served without the token and name no secret, path, host or worker id; a failing check's error is logged at warn. The compose healthcheck and `smoke:e2e` wait on `/health/ready`.

## Checks

```sh
npm run verify        # the CI gate: lint + all-package typecheck + tests + web build + its size budget
npm run check         # alias for verify
npm run format        # format and safe lint/import fixes
npm run test
npm run typecheck
npm run smoke:e2e     # the whole server over HTTP on PGlite, the local driver and the scripted model
JJ_SMOKE_BASE_URL=http://127.0.0.1:3001 npm run smoke:e2e   # the same against a running stack, on the docker driver
npm run smoke:runtime # one live pi tool cycle in a sandbox (local, or JJ_SMOKE_DRIVER=docker); JJ_SMOKE_MODEL (default openai/gpt-6-luna) and its key
npm run smoke:nightly # both smokes on a live model under a hard cost cap, with a summary (see Nightly live run)
npm run test:browser  # the web app's main user paths in headless Chromium, on the scripted model
npm run size -w @jj/web  # the built web app's chunk sizes; fails when the initial JavaScript is over budget, or a lazy-only module loads too early
```

`smoke:e2e` boots the API in-process on a temporary PGlite directory, creates three bots and a task with all of them, follows the task stream to completion, checks that two workers ran in parallel and that every artifact downloads intact, stops a second task, and stops a third at its spend cap (on `scripted/team-priced`), checks the refusal, raises the cap and continues it, then runs a task whose failing check the coordinator fixes until it completes verified, and one whose check cannot pass, which waits unverified. Last, a direct chat asks a bot for a file, which creates one task; the bot tells the result in the chat with the task's card, answers how it went, and a follow-up continues the same task. It exits non-zero on any failure, and prints what the server spent in its last 24 hours (`GET /api/usage`). `JJ_SMOKE_MODEL=<provider/model> npm run smoke:e2e` runs the same flow on a real model whose key is set, checking structure only where a real model words or routes things its own way, and without the check that can never pass. A spend cap that stops work no step expects to stop (the server's `JJ_MAX_USD_PER_DAY`, which the booted server reads from the smoke's environment, or a task's cap) fails that step at once as stopped at the cap. `JJ_SMOKE_TASK_CAP_USD` caps every task of the server the smoke boots (its default profile's `maxUsdPerTask`), and `JJ_SMOKE_REPORT=<path>` writes the steps, their times and the spend as JSON. `JJ_SMOKE_DRIVER=docker` boots that server on the `docker` driver alone instead of `local`, in a daemon namespace of its own whose containers and volumes it removes at the end, also when SIGTERM or SIGINT stops it (it then still reports its steps and spend); it checks that the default profile is the available, isolated docker sandbox and runs it without network, on `jj-sandbox:base-1` or `JJ_SMOKE_SANDBOX_IMAGE`. `smoke:runtime` takes `JJ_SMOKE_MAX_USD`, past which it starts no model call, `JJ_SMOKE_REPORT`, and `JJ_SMOKE_DRIVER=docker` (with `JJ_SMOKE_SANDBOX_IMAGE`), which runs its command in an isolated, ephemeral container without network.

With `JJ_SMOKE_BASE_URL` it boots nothing and drives the server at that URL; `JJ_SMOKE_TOKEN` is its bearer token (for the compose stack, the one in its `Open JJ Bot` line). It then also checks that `docker` is the only driver and the default profile is the available, isolated docker sandbox, that the workers' commands ran as the sandbox user in `/workspace`, and that a sandbox cannot open a TCP connection to any `JJ_SMOKE_UNREACHABLE` target (comma-separated `host:port`, default `app:3001,postgres:5432`). `JJ_SMOKE_RESTART_COMMAND` adds restart survival: a third task's workers are caught running a slow command, the command (such as `docker compose restart app`) restarts the server, and the task must still complete, with the same token, the cut-short commands reported as stopped, the runs handed back and resumed, the files written before the restart still in the workspace, no finished tool call run again, and the stream replayed across the restart folding into the same view a reload returns. `JJ_SMOKE_RESTORE_COMMAND` adds backup survival: after the first task, the command (such as `scripts/backup.sh`, `docker compose down -v` with the sandboxes' volumes, `scripts/restore.sh` and `up` again) replaces the stack with its restored backup; every bot, profile, task view, event and artifact must read back unchanged with the same token, and the restored task, continued with a verification plan whose commands check its files by SHA-256 in the restored workspace, must complete verified. The rest of the smoke then runs on the restored data.

CI (`.github/workflows/ci.yml`) runs on pull requests (on their merge result) and on pushes to `main`, on the Node version in `.nvmrc`, in three parallel jobs. The first, after `npm ci` and a `docker version` check, builds the sandbox base image, then runs lint, typecheck, tests (with PostgreSQL and Docker), the web build, its size budget ([Web bundle size](#web-bundle-size)) and `smoke:e2e` (scripted model only): the `npm run verify` steps plus the smoke. Every step must pass, and once dependencies are installed each runs even when an earlier one fails, so one run reports every failure. The second, "Compose stack", runs `docker compose build` (the app image and the sandbox image), starts the stack with the scripted model and no `API_TOKEN` (`up --wait`, until `/health/ready` passes), reads the generated token from the `Open JJ Bot` line and the app's and PostgreSQL's container addresses, backs up the new stack before any task (a backup without workspaces), and runs `smoke:e2e` against the stack through the published loopback port with `JJ_SMOKE_RESTART_COMMAND="docker compose restart app"` and a `JJ_SMOKE_RESTORE_COMMAND` that backs the running stack up, wipes it (`down -v`, the sandboxes and their volumes) and restores it. It then checks the backup's manifest and that a second restore, into the stack that now holds data, is refused, and that the logs carry the token only in one `Open JJ Bot` line per boot, the same before and after the restart; finally a copy of the backup holding an archive its manifest does not list is refused before anything changes, and `restore.sh --force` replaces the stack's data with the backup's. On failure it prints the stack's logs, and it always ends with `docker compose down -v` and removes the sandboxes' containers and volumes. The third, "Browser", installs Chromium's headless shell with its system libraries (`npx playwright install --with-deps --only-shell chromium`) and runs `npm run test:browser` ([Browser tests](#browser-tests)); when it fails it uploads `test-results/` (each failed test's trace, screenshot and server log, and the HTML report) as the `browser-test-results` artifact. On CI the suite has an 8-minute global timeout, so a hung run fails, and uploads, before the job's 10-minute limit cancels it. A newer run on the same ref cancels the superseded one.

Some tests need external services and skip when those services are missing. CI provides both, so there these tests run instead of skipping:

- PostgreSQL: tests gated on `JJ_TEST_DATABASE_URL`, such as the concurrency tests in `packages/db` and the separate-worker test in `apps/worker`. Each of those suites creates and drops its own database, so the user needs the `CREATEDB` privilege. Locally, point it at a disposable server, never the development one: `docker run -d --rm -p 55432:5432 -e POSTGRES_USER=jj -e POSTGRES_PASSWORD=jj -e POSTGRES_DB=jj_test postgres:17-alpine`, then `JJ_TEST_DATABASE_URL=postgresql://jj:jj@127.0.0.1:55432/jj_test npm run verify`.
- Docker: sandbox driver tests that skip when no Docker daemon is reachable. CI runs on the runner VM with its Docker daemon and fails if `docker version` cannot reach it; it builds the base image with `npm run sandbox:image` and sets `JJ_SANDBOX_TEST_IMAGE=jj-sandbox:base-1`. Locally the tests use that image when it is built and `node:22-bookworm-slim` otherwise. The conformance check that an `allowlist` sandbox reaches a listed public host needs internet access from containers: on a machine without it, `JJ_SANDBOX_TEST_OFFLINE=1` skips that one check with a note. CI never sets it, so the check runs there.

The root `vitest.config.ts` sets 20 s per-test and per-hook timeouts, because PGlite-backed suites are slow on loaded machines, and excludes `.claude/` agent worktrees so a run from the main checkout matches CI. No test calls a live model: the engine suites use a fake executor, the runtime suites pi's faux provider and the scripted model, and the API suites drive the real wiring with the scripted model through `app.request` and a real server. `apps/api/src/web-client.test.ts` runs the web app's `liveApi` against the server, which keeps the client and the routes in step. Live model behavior is covered only by the smoke scripts. See [CONTRIBUTING.md](../CONTRIBUTING.md) for the verification loop and [AGENTS.md](../AGENTS.md) for the issue workflow.

Changes to `packages/contracts` must bump `CONTRACT_VERSION` and add an entry to [the contract changelog](contract-changelog.md).

### Nightly live run

`.github/workflows/nightly-live.yml` catches provider, model and prompt regressions that the keyless checks cannot see. It runs every night at 03:17 UTC and by hand, never on pull requests or pushes, so no pull request, from a fork or not, runs with the provider key. Its token can only read the repository, and its actions are pinned to full commit SHAs. Its one job checks the Docker daemon, builds the sandbox base image (both only when the key is set) and runs `npm run smoke:nightly` (`scripts/smoke-nightly.ts`): `smoke:runtime`, then `smoke:e2e` with `JJ_SMOKE_MODEL` on the server the smoke boots, both on docker sandboxes (delegation to two workers in parallel, stop, spend cap, verification, and the direct chat whose task is told in the chat and continued by a follow-up).

- **Enabling it.** Add the provider key as a repository Actions secret named `OPENAI_API_KEY` (Settings, Secrets and variables, Actions). The workflow hands it to that one step as an environment variable, and nothing prints it. Without it the job skips the Docker steps and passes with a notice and a summary saying it was skipped; the other steps see only whether the key is set. A model of another provider needs its own key's secret, added to that step's `env` too. GitHub runs schedules from the default branch only, and disables them in a public repository after 60 days without activity.
- **Running it by hand.** Actions, Nightly live, Run workflow, with `model` (`provider/model`, default `openai/gpt-6-luna`) and `max_usd` (the cost cap, default `0.25`); or `gh workflow run nightly-live.yml -f model=openai/gpt-6-luna -f max_usd=0.10`. Locally, with the key in the environment or `.env`, a Docker daemon and the sandbox image: `JJ_NIGHTLY_MAX_USD=0.05 npm run smoke:nightly`, with `JJ_NIGHTLY_MODEL`, `JJ_NIGHTLY_TASK_CAP_USD` and `JJ_NIGHTLY_SANDBOX_IMAGE` as well. `GITHUB_STEP_SUMMARY=<file>` keeps the summary there too.
- **The cost cap.** The product's own spend caps keep it. `smoke:runtime` gets the whole cap (`JJ_SMOKE_MAX_USD`); the server `smoke:e2e` boots gets what is left as `JJ_MAX_USD_PER_DAY`, and its default profile caps each task at `JJ_NIGHTLY_TASK_CAP_USD` (default half the cost cap) through `JJ_SMOKE_TASK_CAP_USD`. A model call in flight when a cap is reached still finishes, so the spend can pass the cap by at most one call per session or chat reply running then (`JJ_CONCURRENCY`). Work a cap stops fails its step at once, and the run is reported as stopped at the cost cap and fails. A model with no listed price is refused, since no cap could bound it, and `smoke:e2e` is not started when `smoke:runtime` left nothing of the cap or reported no spend.
- **The summary.** The job summary gives the result (passed, failed, stopped at the cost cap, or skipped), the spend against the cap (`smoke:runtime`'s own count plus `GET /api/usage` of the `smoke:e2e` server), each check's result, cost, model calls and time, and every `smoke:e2e` step with its time and failure; a failure or cap stop is also an error annotation. The script exits 0 when every check passed or the run was skipped, 1 when one failed or a cap stopped it, and 2 for settings that cannot work.
- **Sandbox.** The key is in the environment of the processes that call the model, so no command a model writes may run beside them: on `local`, a command could read it from the server's environment. The script therefore runs both smokes on the `docker` driver whatever its environment says (`JJ_SMOKE_DRIVER=docker`), and fails a check whose report names another driver. `smoke:runtime` runs its one bash command in an isolated, ephemeral container without network. `smoke:e2e` boots its server with `docker` as the only driver, in a daemon namespace of its own, and checks that the default profile is the available, isolated docker sandbox before it sets that profile's network to `none` (no task in it needs network; model calls are the server's). The docker driver passes no key or host environment into a container. The job checks the daemon and builds `jj-sandbox:base-1` (`npm run sandbox:image`) first; locally, `JJ_NIGHTLY_SANDBOX_IMAGE` names another image with bash and GNU coreutils, findutils and grep.

### Web bundle size

`npm run size -w @jj/web` reads the web build in `apps/web/dist` (run `npm run build -w @jj/web` first) and prints every JS and CSS chunk with its raw, gzip and brotli size in kB (1000 bytes), marked `initial` or `lazy`. The initial load is what `index.html` makes the browser fetch before the app runs: its module script, every chunk that script imports statically and its stylesheets; every other chunk loads on demand. The command fails when the initial JavaScript is over its budget, raw or gzipped (`INITIAL_JS_BUDGET` in `apps/web/bundleSize.ts`), which sits about 10% above its size when it was last set. It also fails, whatever the size, when a module that must load on demand is in the initial load, loads with a module it must only come after, or is in no chunk at all. `LAZY_MODULES` lists them by source path or npm package. None of the demo data, the Tasks, Studio and Settings screens, the 3D office and Three.js may be in the initial load, and the 3D office and Three.js may not load with the Tasks screen (its chunk and the chunks that chunk imports statically), only once the 3D view opens. The build's `chunkModules` plugin writes each chunk's modules and static imports to `dist/.vite/modules.json` for this check, as the built code no longer names them; a file imported with a query (`?raw`, `?url`, `?worker`) counts as a module of its own. `npm run verify` and CI run it after the web build. Over budget, load what the first screen does not need on demand (`React.lazy` for a screen, `import()` for a module) or raise the budget deliberately, with the reason in the pull request.

### Browser tests

`npm run test:browser` builds the web app and runs the Playwright suite in `apps/web/e2e` (`*.e2e.ts`, which vitest does not collect) in headless Chromium. It covers the main user paths: creating a bot in Studio and editing it; a direct chat that starts a task, the task update with its card, and a follow-up that continues the same task; a task's Progress, Graph and Office 2D views; a task's verification checks, shown verified only once they pass and never when they cannot; editing a runtime profile in Settings; storing a sandbox secret write-only and granting it, and the notice shown without `JJ_SECRET_KEY`; a call held for approval, approved in the task chat and denied from direct chat; a deep link fetching its screen's chunk while the workspace loads; every screen at 360px on a touch screen, with nothing scrolling sideways and every control a 44px target, and the phone menu's focus order; the 2D-only office without WebGL; and the installable app: the manifest as Chromium parses it, its icons, and a service worker that serves the shell from its cache (offline too), takes a new `index.html` from the network first and never answers `/api`.

- **Isolation.** Every test gets an instance of its own from verify-jj-bot's `launch.sh --no-build` (the API, embedded worker and built app on a fresh PGlite dir, the scripted model, the local driver and a cleared environment) and stops it with `stop.sh`; `test.use({ secretStore: true })` launches it with `--secret-store`, a fresh `JJ_SECRET_KEY`. `baseURL` points at that instance, so tests are independent and run in parallel. A test that needs a bot but is not about Studio creates it through the API, so a Studio regression fails only the Studio test.
- **Determinism.** Tests find elements by role and accessible name, wait on visible state instead of sleeping, and are never retried: a flaky test fails the run. Page helpers are in `app.ts` and the instance fixture in `fixtures.ts`.
- **Service worker.** The built app's service worker runs in every test, as it does for users, and controls the page once it has loaded. `page.route` does not see requests a service worker handles, so a test that intercepts the shell or `/assets` after the first load uses `context.route`, or turns the worker off with `test.use({ serviceWorkers: "block" })`.
- **Running it.** Install the browser once with `npx playwright install chromium` (the build the pinned `@playwright/test` expects). `npx playwright test -c apps/web/e2e [file] [-g title]` runs part of the suite against the existing `apps/web/dist`; `--headed` or `--debug` shows the browser. `npm run typecheck -w @jj/web` checks the suite with its own `tsconfig.json`, which has Node types; the app's does not.
- **Evidence.** A failed test keeps its trace, screenshot and server log under `test-results/browser/<test>/` (`npx playwright show-trace <path>/trace.zip`); a passed test leaves nothing.

## Constraints

- PGlite is single-process. Its data directory is locked to the process that opens it and a second process is refused. A separate worker, or more than one API process, requires PostgreSQL.
- One worker per `JJ_DOCKER_NAMESPACE` on a Docker daemon. At start a worker removes every container and network of its namespace that another process started (`reapOrphans`), so two live workers in one namespace remove each other's sandboxes; an API with `JJ_EMBED_WORKER=true` counts as a worker. Task volumes are named by namespace (`<namespace>-task-<taskId>`), so workers in separate namespaces do not share task workspaces either. Running several workers on one daemon therefore needs a shared-namespace design, in which a worker reaps only containers whose owner is gone ([#45](https://github.com/LemonPhase/jj-bot/issues/45)).
- An `ephemeral` workspace lives in one worker's sandbox. A session of that task claimed by another worker is handed back while the holder's lease is live, and fails visibly once the holder is gone.
- The `local` driver is not an isolation boundary: commands run as the server's user and can read its files, `.env` included, and its environment. Use `docker` for anything but trusted development ([Drivers](../packages/sandbox/README.md#drivers)).
- Writes serialize per task and per bot (sequence allocation row-locks that task or bot), never globally. Job claims use `FOR UPDATE SKIP LOCKED`, and at most one run per session and one chat reply per bot is ever active.
- Pooled PostgreSQL connections set `lock_timeout` (10 s) and `idle_in_transaction_session_timeout` (60 s), so a statement stuck waiting on a lock, or a transaction left open, fails instead of hanging.
- Job leases prevent duplicate execution by competing workers, but they do not make external tool effects exactly-once. Reconcile ambiguous effects before retrying after a crash.
- `npm audit` findings are triaged, not blanket-fixed: review reachability and patched upstream releases before external deployment, never apply breaking overrides wholesale, and never claim a clean audit without running it. An entry in the root `overrides` patches one dependency of one exact parent version (`"<parent>@<version>": { "<dependency>": "<patched version>" }`) within the dependency's major, so upgrading the parent drops it; npm keeps a lockfile entry it already has, so after adding one, re-resolve the parent (remove its `package-lock.json` entries and run `npm install`) and check `npm ls <dependency>`.
