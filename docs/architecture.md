# Architecture

The design contract for JJ Bot: components, boundaries, records and invariants. Terms are defined in the [glossary](glossary.md). Product semantics are in [Product specification](product-spec.md), and package-level contracts in the READMEs of [the engine](../packages/backend/README.md), [the runtime](../packages/runtime/README.md), [the sandbox drivers](../packages/sandbox/README.md) and [storage](../packages/db/README.md). Code and tests establish implementation behavior.

## Components

| Component | Responsibility                                                                                                                                                  |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Web app   | Bot chat, task group chat, execution graph, steering and stop, settings. Renders server state and never runs agent loops. Its service worker keeps no API data. |
| API       | Validates commands, owns product records and message routing, persists events, streams task events.                                                             |
| Worker    | Claims durable jobs, runs execution sessions and chat replies on the pi agent runtime, maps runtime activity to task events, enforces budgets and cancellation. |
| Database  | PostgreSQL, or embedded PGlite for a single process: domain records, the job queue and the append-only task event log.                                          |
| Sandbox   | Where agent tools execute. Provided by a pluggable driver selected by a runtime profile.                                                                        |

The API embeds the worker by default. On PostgreSQL the worker can run as its own process (`apps/worker`) without changing any identity. Execution is never owned by an HTTP request or an open stream: closing the browser does not stop a task.

## Execution model

Each execution session runs pi's agent loop (`@earendil-works/pi-agent-core`) inside the worker, over a transcript the engine owns. Its coding tools — bash, read, edit, write, grep, find and ls — act on the task's sandbox, so the loop and the provider calls stay in the worker while every command and file access happens in the sandbox. ls is pi's tool on sandbox-backed operations; the other six are JJ tools over the sandbox's filesystem API and command execution, because pi's versions resolve paths on the host filesystem, pass the host environment, write host temp files or spawn host binaries. Model credentials are therefore never handed to agent-run code; whether that code can still read them from the host depends on the driver (see [Sandbox boundary](#sandbox-boundary)). The runtime README has the tool and run semantics.

pi supplies the agent loop, steering at turn boundaries and the multi-provider model registry. JJ Bot supplies identity, durability, scheduling, collaboration, the sandbox-bound tools and the event log. The engine reaches pi only through its ports (`SessionExecutor`, `ChatResponder` and `ModelCatalog` in `packages/backend/src/ports.ts`), so the runtime can be upgraded or replaced without touching orchestration.

The loop stays in the worker for every driver, remote ones included. Each command to a remote sandbox costs a network round trip; that latency is accepted in exchange for keeping keys, budgets, steering and cancellation in the worker.

Each bot chooses its own model as a `provider/model` reference resolved through pi's registry. A provider's key comes from its server environment variable or from the [secrets store](#secrets-store), where it was entered in settings; when both exist the variable wins, so the operator's environment is the one authority for a provider it configures, and a stored key is never silently ignored: settings show it as shadowed. Keys are resolved per call, so a key stored or replaced is used from the next run or reply on, and never appear in a transcript. Settings show which providers are configured, where each key comes from and which models they offer; a stored key is write-only, shown only by its last four characters.

## Sandbox boundary

A `SandboxDriver` turns a sandbox spec into a running `Sandbox` that exposes command execution, a workspace filesystem and optional ports, snapshots and metrics. The in-tree drivers are `local` and `docker`; a remote driver, such as one for Daytona, would implement the same contract. The contract lives in `packages/sandbox`.

- **Capabilities are declared, not assumed.** Each driver states what it can enforce: the network modes, resource limits and filesystem isolation, and whether it can run long-lived processes with streamed input and output (`spawn`, which stdio MCP servers need). A spec that asks for more, or that is addressed to another driver, is refused. A driver never silently weakens isolation.
- **The environment is built from scratch.** No driver passes the host or worker environment into a command; declared variables and secrets injected by name are the only additions. Not passing is not hiding: only a driver that declares filesystem isolation keeps the host environment and files out of reach.
- **Paths are contained.** The sandbox filesystem API rejects any path outside the workspace, checked after following symlinks. This constrains the API, not commands: what a command can reach depends on the driver's isolation.
- **Interruption is reported honestly.** A command reports `no`, `yes` or `unknown`. `yes` means the driver verified that none of the command's processes survive; `unknown` means it could not, so the command's effect may already have happened or may still be happening.
- **Long-lived processes stream, within bounds.** A driver that declares `spawn` starts long-lived processes, such as stdio MCP servers, with stdin, stdout and stderr streaming while they run. A spawned process gets the environment, isolation, network policy and contained working directory a command gets, and no timeout. Its output is passed on as it is read and never collected: while nobody listens the driver holds at most 1 MiB and then stops reading, so a process that floods its output blocks instead of growing the worker's memory, and whoever consumes the output bounds what it keeps (a frame cap, a stderr ring). Stopping it sends SIGTERM, then SIGKILL after a grace period, to it and its descendants, and reports `yes` or `unknown` as for a command. Declaring `spawn` is not running MCP servers: bootstrap's `capabilities.mcp` reports whether the server actually does.
- **Release ends everything the sandbox started,** background and spawned processes included, and discards an ephemeral workspace.
- **Conformance is the contract.** A driver is valid when it passes the shared conformance suite.

A task acquires **one sandbox for all its sessions**. The worker's task sandbox manager acquires it once per task, with the coordinator's runtime profile and `workspaceKey` set to the task id, and releases it when the task ends, after it sits idle (`sandboxIdleMs`, ten minutes by default, for a `task` workspace), or when the worker holds more than `JJ_MAX_HELD_SANDBOXES`; sessions never acquire their own. Bots therefore see each other's files immediately, and one runaway process affects the whole task within the profile's resource limits. Bots can also overwrite each other's edits, so the coordinator partitions files: each brief names the files its worker owns, workers edit only those (they may read any), and files several pieces need are edited by the coordinator after the results arrive.

A workspace is identified by its mode and its key. Task execution uses two modes:

- `task` (the default): files persist across releases and restarts, and every sandbox acquired for the task sees them. Only a schedule removes one, through the driver's `removeWorkspace`, for its oldest finished tasks beyond `keepWorkspaces` (see [Schedules](#schedules)); deleting a task leaves its files, and the operator clears the driver's storage (for `local`, its root directory).
- `ephemeral`: the workspace is discarded when the task's sandbox is released: when the task finishes or stops, when the worker stops, after it sits idle much longer than a `task` workspace (`JJ_EPHEMERAL_IDLE_MINUTES`, default 6 hours), or when the worker holds more sandboxes than `JJ_MAX_HELD_SANDBOXES` and it is the least recently used idle one (idle `task` workspaces go first). A session that needs a discarded workspace, or would resume one after a restart, fails visibly.

The contract also defines `bot`, a workspace that persists for one bot across tasks. Task execution never uses it, because it would expose the coordinator's files from earlier tasks to every participant.

The `local` driver runs commands directly on the host, as the server's user. It does not pass the server's environment into commands, but it hides nothing from them: they can read every file that user can, including `.env` and key files, and the server's own environment through `/proc`. Its process cleanup is best effort without cgroups, so a `yes` from `local` is not a guarantee. `local` exists for development on a trusted machine, and the product labels profiles that use it as unisolated.

The `docker` driver starts sandboxes as sibling containers through the host's Docker API. When JJ Bot itself runs in a container, that API arrives as the mounted host socket, which is root-equivalent on the host. The driver therefore never passes the socket into a sandbox, never creates privileged containers and never bind-mounts host paths: workspaces are named volumes, and file access goes through the Docker API. A filtering proxy can sit in front of the socket through `DOCKER_HOST` without code changes (`compose.socket-proxy.yaml` runs one that allows only the API sections the driver calls, on a Unix socket only the app's uid can open, which no host account may share, and on no network), and a call it refuses is reported as refused by a proxy, naming the call; plain-HTTP `tcp://` is refused for a host that is not loopback unless the operator opts in. Such a proxy narrows the API but does not bound what a container create asks for, so whoever drives it is still root-equivalent on the host. A starting worker removes the containers and networks of its docker namespace that other processes started (`reapOrphans`), keeping workspace volumes, so only one live worker may use a namespace on a daemon (see [Constraints](development.md#constraints)).

The docker driver enforces three network modes. `none` leaves a sandbox only loopback. `open` puts it on Docker's default bridge, which reaches the internet and whatever else the bridge reaches, host services on its gateway included. `allowlist` gives each sandbox its own internal network, on a small subnet of the driver's own pool, with no route out, no external DNS and no address on the host. Its only other member is an egress proxy the driver starts beside it. The driver checks the network and the sandbox (no host address, no IPv6) instead of trusting the engine version, and refuses the sandbox when a check fails. The sandbox reaches the outside only through that proxy, as an HTTP(S) proxy (`HTTPS_PROXY`), and the proxy forwards only to listed hosts and ports. It resolves names itself and refuses any target that resolves to a non-public address, so the app, PostgreSQL, the Docker host and cloud metadata stay unreachable even when listed. Proxy-unaware clients, raw TCP (ssh, `git://`) and private destinations do not work in `allowlist`. The proxy holds no secrets and is hardened like a sandbox; it is removed with the sandbox. The [driver README](../packages/sandbox/README.md#network-mode-allowlist) has the details and limits.

## Runtime profiles

A runtime profile is the user-facing record that decides how a bot executes: the sandbox driver and spec (image, resources, network policy, workspace lifetime), the coding tools and [sandbox secrets](#secrets-store) it grants, budgets (model calls per run and minutes per run), spend caps (per task, and per bot over any 24 hours; see [Spend caps](#spend-caps)), approval rules (calls that wait for the user's approval; see [Approvals](#approvals)), and the MCP servers and skills it grants (see [MCP servers and skills](#mcp-servers-and-skills)). Collaboration tools come with a session's place in the task, not with a profile: `delegate` and `message` when the task has teammates (`delegate` only while the session's depth is below the delegation limit), `complete_task` for the coordinator alone, and the read-only lookup tools (`task_state`, `task_log`, `read_entry`, `read_report`; see [Context and memory](#context-and-memory)) for every session. Users create and edit profiles in settings; a bot references one, or uses the default profile. The profile is the single place where isolation and spending are configured. The API reports each profile's status from its driver: whether the driver is available, and whether it isolates the filesystem. A profile without filesystem isolation is labelled unisolated. Within a task, the shared sandbox uses the coordinator's profile, while each bot's own tools and budgets still apply to its sessions.

On first boot, with no profiles stored, the server seeds one profile per registered driver, each with every coding tool and the default budgets (60 model calls and 30 minutes per run, $5 per task and $20 per bot per 24 hours): **Docker sandbox** (`jj-sandbox:base-1`, network `open`, `task` workspace, 2 CPUs, 2048 MB, 512 processes) and **Local (unisolated)** (network `open`, `task` workspace). Docker is the default when its daemon answers at that boot; otherwise local is, when registered.

## Secrets store

Keys and credentials entered in settings are kept in the `secrets` table, encrypted: provider keys, named by provider, and **sandbox secrets**, named by the environment variable they become (`GITHUB_TOKEN`). No answer of the API, event, log line or client ever carries a value: settings show a name, the last four characters and when it was set.

- **Encryption.** Each value is sealed with AES-256-GCM under a key derived (HKDF-SHA256) from the server's master key, with a fresh random nonce on every write, and bound to its row (owner, kind and name) as associated data, so a ciphertext copied onto another row does not open. Each row names the key that sealed it by an HMAC of that key, never the key itself.
- **The master key** is `JJ_SECRET_KEY`, base64 of at least 32 random bytes, and only the server's environment holds it: it is never stored or generated. A database or a backup alone therefore reveals no value: of each one it holds in readable form only the last four characters (`hint`) and the length, which the ciphertext's own length gives away. Without it the store is off: nothing can be stored, `capabilities.secretStore` is false, writes answer 409 `SECRET_STORE_UNAVAILABLE`, and settings say how to set it; keys from environment variables work as before.
- **Rotation.** The previous key goes in `JJ_SECRET_KEY_PREVIOUS`; every process reads with both, and when it starts the engine seals again, under the current key, every row a previous key sealed, retired values included. Rotating the master key does not change the values: a value that leaked with its key is revoked where it was issued.
- **Loss.** A row no configured key opens is kept, listed as unreadable and used nowhere: its provider is not configured, and a sandbox whose profile grants it does not start. The server warns at boot, naming such rows and never their values. Storing the value again under the current key, or removing it, clears the state. Nothing is deleted silently, and a value whose key is lost is unrecoverable.
- **Values** are one line of 16 to 4096 characters, so every stored value is long enough to redact wherever it appears. A sandbox secret may not take a variable the sandbox, its shell or its proxy sets, or one that changes how programs load (`PATH`, `*_PROXY`, `LD_*`, `JJ_*` and the like), nor hold or be part of a model key, the API token, the database password or the master key (`Bearer <key>`, a line of an `.npmrc`), and a provider key may not hold or be part of a sandbox secret's value: a model key never enters a sandbox, even as a copy. A value refused as a server secret gets one refusal, the same whichever server secret it matches, current or retired, which names none of them: the refusal never tells which secret a value matched, nor whether a model key it matched is current or replaced.
- **Retired values.** A value that is replaced or removed, a provider key or a sandbox secret, is retired in the same transaction: sealed again under the current key into `retired_secrets`, bound to that table as associated data, so it never opens as a current value. A retired value is used only to redact it and, for a provider key, to refuse it as a sandbox secret: it is never injected, granted or answered back, and settings never list it. A task can still print it after every sandbox that held it is released (a file it wrote, a shared `/tmp` on `local`), so every redactor covers it. It is kept for 90 days after it was retired, long enough to outlive the sandboxes and work of the tasks that ran with it and the revocation of a rotated credential where it was issued, then deleted at the next boot or the next retirement. A name keeps one retired row per value: retiring a value again moves that row's time. A name also keeps at most its 10 most recently retired values: retiring another deletes the oldest, which is then no longer redacted nor, for a provider key, refused as a sandbox secret. Every redactor covers each retired value at a cost on everything a run stores, so a name replaced often (a script rotating it hourly) adds at most 10 values, not one per replacement for 90 days. Nothing else purges retired values. Storing the same value again retires nothing, and a value no configured key opens is not kept, since it was redacted nowhere. A retired value no key opens any more is counted, never named or shown, in a warning at boot and in the data check. A retired provider key counts as a server secret for those 90 days, since a rotated key may not be revoked yet: no sandbox secret may hold or be part of it, nor reach a sandbox if one does.
- **Grants.** A runtime profile grants sandbox secrets by name (`secrets`). A grant must name a stored secret and may not share its name with an entry of the profile's `sandbox.env`, and removing a secret removes its grants in the same transaction. A task's sandbox is acquired with its coordinator's profile, so that profile's grants are what the sandbox gets, and every command in it, whichever bot runs it, sees them: commands of one sandbox can read each other's environment, so a grant per session would be no boundary. The worker decrypts the grants when it starts the task's sandbox and hands them to the driver, which injects them into each command (never the docker container's configuration, nor the driver's own helper commands). A changed or removed secret reaches a running sandbox only when it is acquired again, after it is released; until then the sandbox keeps the values it started with, and every run in it redacts those values as well as the stored ones.

## Domain records

| Record            | Responsibility                                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Bot               | Identity, role, instructions, model choice, runtime profile, appearance, memory.                                                                       |
| RuntimeProfile    | Sandbox driver and spec, coding tools, budgets, spend caps, approval rules, MCP servers, skills; reports driver availability, isolation.               |
| McpToolSnapshot   | The reviewed tool list of one MCP server for one configuration. Immutable; a profile's server pins one.                                                |
| McpDiscovery      | One test of an MCP server configuration: queued, running, succeeded with its snapshot, or failed with a redacted error and stderr tail.                |
| Skill             | A skill in the library: its files, description and content-addressed version. Granted by profiles by name.                                             |
| BotConversation   | Direct user-to-bot chat outside task execution.                                                                                                        |
| ChatTaskUpdate    | A task event its coordinator's chat is told (completed, failed, waiting for the user, a call waiting for approval) until a reply answers it.           |
| Task              | Title, goal and goal version, verification plan, coordinator, state, final result, stop request, spend cap, the template and schedule it started from. |
| TaskTemplate      | A saved task setup: title, goal, coordinator and participants, verification plan, spend cap. Its problems are derived on read.                         |
| Schedule          | A template started on a cron schedule in a time zone: instructions, overlap, kept workspaces, chat updates, next fire, pause.                          |
| ScheduleFire      | What the scheduler did about one due time of a schedule: started, skipped, missed or refused, with the task or the reason.                             |
| TaskParticipation | Bot membership in a task.                                                                                                                              |
| ExecutionSession  | Task, bot, parent session, role, brief, depth, goal version, status, what it waits for, result.                                                        |
| SessionEntry      | One entry of a session's pi transcript: a pi message or a compaction checkpoint.                                                                       |
| InboxItem         | Input waiting for a session: a brief, a result, steering or a message, delivered at its next turn boundary or run.                                     |
| Run               | One execution or resumption of a session. Separates context lifetime from execution attempts.                                                          |
| Message           | Attributed author, task or conversation, sequence, intent and recipients.                                                                              |
| TaskEvent         | Ordered durable activity. The single source for chat, the execution graph and the audit trail.                                                         |
| Artifact          | A workspace file or spilled tool output, credited to the run that wrote it, or task-level when no run can be.                                          |
| VerificationCheck | One criterion of a plan evaluated once at one gate attempt of one goal version: outcome and evidence. Append-only.                                     |
| Usage             | Tokens and cost per model call (compaction summaries and chat replies included), attributed to session, run, bot.                                      |
| Approval          | A call that waits, or waited, for the user's approval: session, run, tool call, goal version, the user's answer, how it ran.                           |

There is no separate assignment record: a delegated assignment is an execution session (see [Coordination](#coordination)). A bot's appearance is cosmetic and never affects execution. How artifact snapshots credit files is in the engine README.

Records are relational tables with indexed foreign keys. Every record carries an owner so multi-user support is additive. Runtime identifiers (pi sessions, sandbox ids) map to application records; they never replace a JJ Bot identity.

Records outlive the build that wrote them. The schema changes only through forward-only migrations, which the server applies when it opens the database; a build reads every record the previous release wrote, events and transcripts included, and refuses to start on a database that records migrations newer than it ships. The database and the task workspaces are the state to back up; the secrets store's master key is kept apart from them ([Backup, restore and upgrades](development.md#backup-restore-and-upgrades)).

## Direct bot chat

A direct message to a bot runs a lightweight pi session with the bot's persona and model, no sandbox, a bounded history and the chat's task tools. The bot can answer directly, ask a clarifying question, or shape a task's goal and roster before creating it. A bot coordinates the tasks it creates from chat. Task creation from chat is rate-limited. The chat prompt gives the count of the bot's unfinished tasks and points to `list_tasks`; it does not list them. In the history a reply sends, a past reply with a task card names that task (its id and title) in a note, as the card shows it to the user. JJ Bot attaches cards itself, so a note a reply copies is removed before the reply is stored. That history alternates between the user and the bot and starts with the user, as every provider accepts: consecutive messages of one side are joined. A reply that created, continued or stopped a task carries that task's card, and so does one that looked up exactly one task.

The task tools cover only the tasks the bot takes part in (its participations); any other task id, known or not, is refused with a tool error:

- `list_tasks(status?, limit?)`: the bot's tasks, newest first, each with its id, title, status, the bot's role, when it last changed and its result or error on one line.
- `get_task(id)`: the task state as a session's `task_state` gives it (goal and goal version, status, result or error, each session's bot, role, status and the first line of its brief), the bot's role, and the latest task log entries as an index.
- `read_task_log(id, …)`: the task log as `task_log` pages it (newest entries by default), or one entry in full. Session transcripts are never read.
- `create_task`: as above.
- `send_to_task(id, text)`: passes the message on to the task's coordinator, continuing a waiting, completed or failed task as a user message does: same task, workspace and coordinator transcript. A cancelled or stopping task refuses it.
- `stop_task(id, reason?)`: stops the task as the user's stop does. Only the task's coordinator can.

The read tools change nothing, and their output is never a reply's text when its budget cuts it short. Tool definitions are the same whatever tasks exist: task ids are plain string parameters checked inside each tool. A reply takes at most six model calls: the deepest planned reply, a question about a task, takes four (`list_tasks`, `get_task`, `read_task_log` for an entry in full, then the answer), and the other two absorb a refused call and its retry.

**Task updates.** When a task completes, fails or waits for the user, or one of its calls waits for the user's approval, its coordinator tells the user in its direct chat, in its own words (a scheduled task set to `attention` tells no completion; see [Schedules](#schedules)):

- The transaction that changes the task records the update (the task, what happened, and its result, error or the coordinator's question, as stored then and clipped) and enqueues a chat reply for the coordinator. Each event has one update, keyed by the task and its event sequence; a task that continues and then waits again is a new event.
- A later event of the task closes its updates not told yet, and a waiting update whose task no longer waits (the user answered it, in the task or from chat) is dropped, as is an approval update whose approval is no longer pending, so no stale update is told. The reply's input states the task's status now.
- The update is the input of one chat reply and is never stored as a chat message. That reply gets the read tools only; it may suggest an action, and the user decides. Its message carries the task's id, so the chat shows the task's card under it.
- A bot's chat replies run one at a time, each answering one input: the user's unanswered messages first, then the oldest update. An update, or a user message, that arrives during a reply is answered after it, by a reply that sees both.
- The reply that answers an update marks it answered in the transaction that stores its message, so a crash or hand-off tells it once. If the reply fails (a model error or the budget), or its job keeps dying, the engine posts the update as a plain message with the task's card instead, so it is never lost. A user message whose reply failed is not answered again until the user writes more, and its error stays in the conversation view until then, whatever replied since.

The task card reads the live task summary: it shows the task's current status, not its status when the message was written, and a completed or failed task's result or error, or a waiting task's question. The newest card of a task in the conversation also lists the task's calls waiting for approval (`pendingApprovals`), with Approve and Deny: the user answers there as in the task. The bot cannot answer them, and `send_to_task` does not. The summary of a task waiting for the user carries that question (`question`): the coordinator's last message to the user (a discussion message its root session posted with no recipients), redacted and clipped, derived from the task log and gone once the task continues or finishes.

## Visibility is separate from activation

Each task message is persisted once, with attribution and intent, in the task log. The user sees the whole task log. A session is pushed only what reaches its inbox: its brief (for a child session, with the task log so far and the user's messages; see [Coordination](#coordination)), results, steering, and messages addressed to it or to everyone (a message with no recipient goes to every other active session of the task). A session keeps at most its 20 newest undelivered messages; older ones reach it as one `[N earlier messages omitted]` line, and stay in the task log. Beyond its inbox, every session can pull its own task's shared record with read-only lookup tools: the whole task log, including messages not addressed to it, and any session's brief and report (see [Context and memory](#context-and-memory)). Other sessions' transcripts stay private. Pulling delivers nothing and wakes no one.

Delivery is separate from activation: only briefs, results and steering start or continue a run, while other messages ride along with the recipient's next turn, in the order they reached its inbox, and never launch work by themselves. A message alone never gives a model that has ended its turn another one, after a crash or restart too: one that reaches a session then is taken with a brief, result or steering that continues the run anyway, and otherwise waits for the session's next run. A session that finishes before reading a message, because the message arrived during its last model call, hands it to its parent with its result or failure, quoted, so every message the engine accepts is read by its recipient or passed on. A long one keeps its start and its end and names its entry for `read_entry`. The messages the session's inbox left out are counted (the count may include messages to everyone), and the parent gets the `task_log` query that finds them among the task's messages. A message to everyone the inbox kept is not handed on: the parent received it too, or sent it. A coordinator never completes with one unread: it completes only once every delegation has reported, every other session of the task works under one of them, and a message such a session sends reaches the coordinator's inbox before that delegation's report does, so it is taken with the report or before it. This prevents acknowledgement loops and unbounded reply chains.

A message to a teammate with no active session in the task, because its sessions have finished or it never had one, is refused: no bot would read it, so it is not posted, and the sender gets a tool error that says so and suggests `delegate` (or its report, when it cannot delegate). A broadcast is never refused: it reaches every other active session, and is posted even when there is none. Bots are told not to leave anything important only in a message: what a teammate or the coordinator must know goes in a brief, a report or a workspace file.

Message intents: discussion, assignment, result, steering and notification. A bot's message with no recipient (a broadcast) is a notification; a coordinator's reply to the user is a discussion message with no recipient.

## Coordination

Every task has one coordinator, which delegates bounded work and delivers the consolidated task result: the bot the user names when creating the task, or the bot that created it from direct chat.

Delegation creates a child **execution session** for the assignee bot. Its parent is the requesting session, its brief is the assignment, and its result is the assignment's result; there is no separate assignment record. Delegated sessions can delegate in turn, and the session tree is the task's execution graph.

A child session starts on one inbox item, its **first input**, so it knows what the task already holds without the delegating bot relaying it. The engine builds it once, when the delegation is made, from the stored records, and puts its sections in this order, each left out when it has nothing to show:

1. **The task log so far**, as an index: the newest 20 entries before the child's brief, one index line each (the `task_log` format, with a 100-character preview), oldest first. Older entries collapse into one `(N earlier entries — use task_log with before "<id>" …)` line.
2. **The user's messages** in the task, each whole under its entry's id and author: the newest ones that fit within 10 messages and 4,000 characters. Older ones collapse into one line that points at `task_log` with kind `user`. A newest message too long on its own keeps its start and its end around a line that counts the characters left out, and points at `read_entry`. The 4,000 characters are a deliberate bound on "in full": a request longer than that is one `read_entry` away. The heading says whether every message is shown whole, and that the user wrote to the coordinator while the brief says which part of the work is the child's.
3. **The handoff note**, when the bot has reported to the delegating session before (below).
4. **The pointer to the brief**, which is in the child's prompt, ending with the instruction to start.

So the first child of a task whose log is empty starts on the pointer alone. Text other bots or the user wrote is quoted line by line (`> `), so it cannot pass for the engine's own lines; a line ends at any break a model may read as one (CRLF, CR, LF, VT, FF, NEL, LS or PS), and previews are single lines. Bot names and roles appear unquoted (names in entry headers, index lines and the handoff note; both in the persona line, the roster and the `delegate` and `message` tool descriptions), so the contract keeps both to one line of plain text. They refuse every control character (`\p{Cc}`: LF, CR, VT, FF and NEL among them), LS and PS, the Bidi_Control set (U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069), the invisible U+180E, U+200B, U+2060–U+2064, U+206A–U+206F, U+FEFF and U+FFF9–U+FFFB, the tag characters U+E0000–U+E007F and lone surrogates; ZWNJ and ZWJ (U+200C, U+200D) are allowed. Everything shown is redacted before it is clipped. The bounds hold however long the task runs, and what they leave out stays one `task_log` or `read_entry` call away. The first input appears only in that inbox item: the child's stored brief and the task log's assignment message stay what the delegating bot wrote, and input after it reaches the child through its inbox like any other.

Shared decisions are settled in briefs. Before delegating pieces that share something (an interface, a naming or style convention, a data format), the coordinator decides it and states it in every affected brief, alongside the files each worker owns, rather than leaving workers to agree it between themselves. Inside its own piece, a worker decides. A worker that needs a shared decision changed says so in its report, or messages its requester.

Re-delegating to a bot that has already reported to the delegating session still creates a new child session (delegation never reopens a finished session), and its first input carries a **handoff note**. The note is about one session only: the bot's latest session under the same parent that completed or failed. It gives that session's id, the goal version it worked to when that is older than the task's, its brief, its report or, for a failed session, its error, and the `read_report` call that shows them in full. The brief and the report (or error) are quoted like other text in the first input. They are redacted before they are clipped, and their quotes take at most 1,500 and 2,000 characters: a longer one keeps its start and its end around a line that counts the characters left out. The note is a pointer, not a summary: the earlier work stays readable through the lookup tools and in the workspace. The note is built with the rest of the first input, after the user's messages and ahead of the pointer to the brief. A bot with no such session under that parent gets no note: on its first delegation from that session, or while its earlier sessions there are still open or were cancelled. Sessions of the bot under another parent never count.

When a child session finishes, its result is posted as a result message that activates the parent session. The parent resumes from its persisted transcript with the result in context, so it can react to each result as it arrives — re-delegate, correct, or follow up — rather than only after all work ends. A session that ends its turn is `waiting` until input arrives, and records what it waits for: the results of its open delegations, the user, or the user's approval of a call it holds (see [Approvals](#approvals)). A waiting session holds no lease and no concurrency slot, so waiting parents cannot starve their children.

Results are delivered, never polled for, so the engine parks a session that polls the task while its delegations are open: it ends the session's run as if the session had ended its turn. It counts a run's polling turns: turns whose calls include a task lookup tool or `complete_task` (refused while a delegation is open) and are otherwise only the read-only coding tools (`read`, `grep`, `find`, `ls`). A turn of those coding tools alone is exploring the workspace, which a session may do while its delegations run: it neither counts nor starts the count over. Any other call is work and starts the count over, including a call to a tool added later. So does a brief, result or steering the session's inbox delivers; a message does not, since it wakes no one. At the third polling turn, if the session still has open delegations, none of that turn's calls runs: each gets a tool error saying the engine ended the turn to wait (one whose arguments are invalid gets pi's validation error instead), the turn's text is not posted, and the session waits for its delegations. A session that only polls its open delegations therefore makes at most three model calls before it waits, and a result wakes it as usual. A session is never parked while it does work at least every third polling turn; since `bash` and `message` are work whatever they do, a session that polls through them is not parked either, and only the turn budget and the spend caps bound it. The decision is made from tool names, before any call of the turn runs or is asked about for approval, and tool definitions do not change. A turn that parks holds no call, since none of its calls runs. A turn that holds a call is never parked: its run ends `held`, and the count starts again in the next run.

The coordinator completes the task by calling `complete_task` with the consolidated result; ending a model turn is not completion. A task with a verification plan completes only when every check of its plan passes: the worker runs them in the task's sandbox once the coordinator's turn ends, delivers a failed or inconclusive attempt to the coordinator as a result it must act on, and leaves the task waiting for the user after the last attempt of a run (see [Verification](verification.md)). Input that reaches the coordinator after it called `complete_task` but before its run ended sets that completion aside, and the coordinator is told so with the input, so it calls `complete_task` again once it has dealt with it. A coordinator that ends its turn without calling it, usually to ask the user something, is waiting for the user, and once no work is active the task is `waiting`; the user's next message continues it. A completed or failed task continues the same way. Only a cancelled task, or one being stopped, is terminal. See [task continuation](task-continuation.md).

Configurable limits cap sessions per task, delegation depth and concurrent execution. Excess concurrent runs queue. A delegation that would exceed the session or depth limit, that repeats one of the caller's open delegations exactly (same assignee and brief), or that follows `complete_task` in the same run, is refused, and the refusal returns to the model as the tool's error so it can adapt. The caller's open delegations are listed in each `delegate` result and in each result delivered to it, never in a tool description: tool definitions stay identical across a session's runs, since they lead the model's prompt cache. Cancelling a task cancels its open sessions.

## Steering and cancellation

Steering is posted to the task chat and reaches the coordinator. Steering is injected into a running session at its next turn boundary rather than discarding its work. A change to the goal or its verification plan increments the goal version, and work or evidence at an older version cannot complete the task.

Stop marks cancellation durably (`cancelRequestedAt`), prevents new launches and new messages, propagates to active sessions and their sandboxes, and records what actually stopped. Cancellation does not undo completed external effects, and a command that could not be interrupted is reported as such.

## Spend caps

No model call starts once a cap it falls under is reached. Three caps apply, all over the priced spend recorded in `usage`:

- **The task's own** (`task.spendCapUsd`): copied from the coordinator's profile (`budgets.maxUsdPerTask`, default $5) when the task is created, or given by the creator, and changed with `PATCH /api/tasks/:taskId`. Null means no cap.
- **Each bot's, over any rolling 24 hours** (its own profile's `budgets.maxUsdPerBotPerDay`, default $20): task sessions and direct chat together.
- **The instance's, over any rolling 24 hours** (`JJ_MAX_USD_PER_DAY`, unset by default): everything.

Stored profiles without the cap keys take the defaults, so no install is unbounded unless a profile says so. One guard is asked before every model call: each turn of a session run, each compaction summary call, the retry after a context overflow and each call of a chat reply, to the user or to a task update. A refused call is never sent and reports no model events. A call in flight is counted when it finishes, so a task can pass its cap by the calls already running: at most one per running session.

At a cap, the session's run ends like a run at its turn budget, and `spend.capped` records which cap stopped it and by how much: once per cap (its scope and value, and the bot for a bot's cap) in each stretch of the task's work, however many sessions it stops, until a user message continues the task. A worker reports what it has, its result marked as stopped at the cap; its parent reacts to it like any result, and is stopped by the same cap at its next call. A coordinator left with no open delegations waits for the user, and the engine posts a system message naming the cap and what lets the task go on, so the task is `waiting`, not `failed`: no delegation or transcript is lost. A bot's cap stops only that bot's sessions, and a delegation to a bot that could make no model call is refused up front with the cap, so no session starts only to stop. While a cap would refuse the next call, the API answers 409 `SPEND_CAP_REACHED` (with the scope, the spend and the cap) to a message that would continue the task, to a task whose coordinator is at its cap, and to a direct message to a bot at its cap. A chat reply the worker refuses fails visibly; a refused task update reply is told by the engine's plain fallback message instead, without a model call. A reply's calls are recorded as each one finishes, so one that fails, or whose update is overtaken, still counts every call it made. Raising or clearing a cap continues nothing: the user's next message does.

At 80% of the task's cap (`SPEND_SOFT_THRESHOLD`) the engine records `spend.threshold` once per cap value and clients show the spend amber. It is a warning only: nothing waits for the user there ([#106](https://github.com/LemonPhase/jj-bot/issues/106) proposes an optional approval past it).

Amounts next to a cap are shown, in the engine's messages and in clients alike, with enough places that spend over a cap never reads as at or under it (`$4.996 of $5.00`). Costs come from the model catalog's listed prices. A model with no listed price (pi-ai prices it at zero) may be free or may not, so its calls are recorded as unpriced and counted in `Usage.unpricedCalls`, never as free. They are not refused, and no cap can bound them; clients say so wherever cost is shown. Calls stored before caps existed with tokens but no cost count as unpriced too. The turn and time budgets still apply.

Usage is reported per task and per session in the task view, and per instance, bot (direct chat apart) and model over the last 24 hours, 7 days and 30 days by `GET /api/usage`, with the caps that apply.

## Approvals

A call can wait for the user's approval before it runs. The bot's own runtime profile lists approval rules (`approvals: [{ tool, match? }]`, none by default): a rule matches every call of its tool (a coding tool, an MCP tool, or every tool of an MCP server; see [MCP servers and skills](#mcp-servers-and-skills)), or with `match` only the calls whose subject contains its text (the command for `bash`, the pattern and path for `grep` and `find`, the path for the other file tools, and for an MCP tool the keys and string and number values of its arguments, unescaped; case-sensitive, `*` for any run of characters, runs of whitespace counted as one). The matcher is the contract's pure `approvalRuleMatches`, so the profile editor previews a rule as the server applies it. Rules guide a cooperative model; they are not a security boundary: a command can reach the same effect in a way no text rule foresees, such as a script it wrote. The sandbox and its network policy remain the boundary.

- **Hold.** The runtime asks the engine before each call runs, after its arguments are validated (`RunHooks.reviewToolCall`). For a call a rule matches, the engine records a pending approval mid-run, in a fenced write of its own before any call of the batch runs (task, session, run, tool call id, goal version, the arguments with the server's secrets redacted, a summary, the rule, and the bot's text from the same message), emits `approval.requested` and records a task update for the coordinator's chat. A call of a response cut at the output limit is never held: pi refuses it, since its arguments may be cut off. An approval is bound to the goal version the run's model last read: the task's when the run's prompt was built (a worker's included, which reads the current goal though its session keeps the version it was delegated at), or the new one once a coordinator is handed steering that changes it. A call made at an older version than the task's (the goal changed while the run was making it) is recorded already expired and answered at once: it never waits. A later run reads the new goal, so its calls wait as usual. The call does not run, reports no tool events, and its result is never stored, so the transcript keeps it unanswered. The rest of its batch runs, then the run ends `held`. A session holds at most one: a second matching call in the same batch is refused with a tool error saying so.
- **While pending.** The session is `waiting` with `waitingFor: "approval"`, holding no lease and no slot, and it starts no run until the user answers. A `complete_task` in the held batch waits with it: the verification gate does not run, and when the session resumes the completion is set aside, so the coordinator completes again once it has the answer (and the checks then run). A wake finds it holding and completes without a run (a worker restart that left its run open closes that run first), so results, steering and messages wait in its inbox. Other sessions keep working. Once no session of the task is queued or running, the task is `waiting` for the user. A user message to a coordinator that holds a call is queued: it neither reopens the task nor answers the approval, and it reaches the coordinator with the answer.
- **The answer.** Only the user answers (`POST /api/tasks/:taskId/approvals/:approvalId`, from the task chat or the chat task card), once: an approval that is no longer pending answers 409 `APPROVAL_NOT_PENDING`, and a stopping or stopped task 409 `TASK_TERMINAL`. The chat task card offers Approve only when the summary is the whole call (`shownInFull`: a one-line bash command within the summary limit, with no character a reader cannot see); otherwise it links to the task, whose card shows all of it. Cards write each such character (controls, bidirectional controls, zero-width and other invisible characters) as its code point (`visibleText`), so what they show is what runs. No agent tool, in a task or in direct chat, can answer. Approving or denying wakes the session.
- **Approved.** Before its first model call, the session's next run claims the call in a fenced write (`startedAt`, once) and runs it with its arguments as stored, which are what the user saw: a server secret the model wrote is never sent. It reports the usual tool events, stores the result as soon as the call finishes and records its outcome on the approval, then goes on with its inbox like any run. A run that finds the call claimed by an earlier one answers it as interrupted with an unknown outcome: it may have run, so it never runs again; so does a session that ends while its started call never reported. A call pi refuses without running it (its tool no longer granted, invalid arguments, or a response cut at the output limit) is recorded as refused (`outcome.refused`), not as a failed run. A restart while pending loses nothing, since the approval and the waiting session are stored.
- **Denied, expired, cancelled.** A denial reaches the model as the call's error result, with the user's reason when they gave one, and the session goes on. A goal or plan change expires every approval made at an older goal version that has not run, pending or approved and not yet started (one whose result already reached the transcript is left as it is), and wakes its session with an error result saying so: a call approved for the old goal never runs for the new one. A session that finishes (stopped, failed or completed) cancels its pending approval, and an approved call it had not started. None of these ever run.
- **Shown.** The approval is the record clients show: every change emits `approval.updated` with the whole record, and the task view carries the task's approvals. The task chat shows each where it was requested, with the whole call, the rule and the bot's text, and a state that never claims more than the record holds: waiting and not run, approved and not yet started, running, ran (with the exit code), interrupted with an unknown outcome, denied, expired or cancelled. Task summaries carry the pending ones (`pendingApprovals`), `task_state` and `get_task` show a session's held call, and the activity line reads "Waiting for your approval".

Approvals bound to their goal version and session survive restarts in the `approvals` table; the task event log is their history.

## MCP servers and skills

A runtime profile can extend its bots with [MCP servers](glossary.md#settings-and-records) (`mcpServers`) and skills (`skills`), configured on profiles only, like tools and approvals. Support is reported, never assumed: bootstrap carries `capabilities.mcp` (`stdio`, `remote`) and `capabilities.skills`, and while one is false a profile asking for it is refused with 422 `MCP_UNAVAILABLE` rather than saved as if it worked. The routes below are served only by a server that reports the capability they belong to; one that reports it false answers them 404. The contract is in `packages/contracts` (`mcp.ts`, `skills.ts`).

- **Configuration.** A profile holds at most 8 servers with unique names: lowercase letters and digits with single underscores between them, starting with a letter, at most 24 characters, so a name never contains `__`. Each has a user-written `description` (the only text of a server's that can enter a prompt), `enabled`, an `exposure` (`direct` declares its tools, `hidden` does not) with per-tool overrides in `toolExposure`, a per-call `timeoutSec` (default 60), `askUnlessReadOnly` and `snapshotId`, its reviewed tool list (null: no tools are declared).
  - `stdio`: one executable (`command`, `args`, a workspace-relative `cwd` without empty, `.` or `..` parts), non-secret `env`, and `secretEnv` (`VAR: secretName`), whose every secret the same profile must grant in `secrets`. The value is expanded inside the sandbox, so it never travels in argv, events or logs. A variable takes any POSIX name except `JJ_*`, which the drivers keep for themselves: the process runs in the sandbox, so `PATH` or `NODE_OPTIONS` is its own business. `startupTimeoutSec` bounds the start.
  - `http` (Streamable HTTP; legacy SSE is refused): an `https://` `url`, non-secret `headers`, and `secretHeaders` (`Header: { secret, prefix }`), whose secret is stored and never granted to a sandbox. The URL and plain headers are stored and shown in the clear, so a credential belongs in `secretHeaders`. A check of names catches the usual mistakes: a URL with a user or password, or with a query, fragment or path `;` parameter (split on `&` and `;`) named like a key, token, secret, password, auth, signature or code, is refused, and so are plain `Authorization`, `Proxy-Authorization` and `Cookie` headers and any header named that way. It looks at names only, so a secret under an unusual name, or written into the path itself (`/sk-live-…/mcp`), is not detected. A URL with control characters or backslashes, which parsing would drop or read as `/`, is refused, and a URL is stored normalized, a non-ASCII host as punycode (`xn--…`), so a look-alike host shows as one. Headers the transport sets (`Host`, `Accept`, `Content-Type`, `Mcp-Session-Id` and the like) are refused.
  - `askUnlessReadOnly` (on by default for `http`, off for `stdio`) asks before calls the server does not mark read-only. The marks come from the server, so the switch guides a cooperative model; approval rules are the boundary.
- **Where servers run.** A stdio server runs in the task's sandbox as a long-lived process, which needs a driver that declares `spawn`; on `local` it is unisolated like any command there. A remote server is called by the worker, never by the sandbox: its credentials never enter a sandbox and tool calls are the only way to reach it, so an approval rule without `match` on its tools stops the effect itself. A rule with `match` is a text check there as well, which a call can evade, for instance by splitting a value across keys, as with bash. The worker reaches it over https only, at its configured origin only, without following redirects, with every response capped at 4 MiB, and at public addresses only: an address in the URL, and every address the name resolves to, must pass the egress proxy's `isPublicAddress`. A direct connection checks the name as it connects and is pinned to an address it checked, so nothing resolves the name again. Through an outbound proxy (`HTTPS_PROXY`, unless `NO_PROXY` names the host) the proxy resolves the name and opens the connection, so it cannot be pinned: the worker still refuses a name it resolves to an address that is not public, leaves a name it cannot resolve to the proxy, and sends the request only once a certificate valid for the name is presented, so a name that resolves differently for the proxy reaches at most a TLS handshake elsewhere. That last limit does not hold for a proxy that intercepts TLS (its CA in `NODE_EXTRA_CA_CERTS`): the worker then checks the proxy's certificate and the proxy alone checks the server's. What the proxy reaches is the operator's egress policy. A response stream that ends before its answer fails that call as cut short (`interrupted: unknown`); it is never resumed, and a call's stream closes when the call times out or is stopped. `JJ_MCP_REMOTE=off` turns remote servers off. A connection belongs to one task sandbox (or the worker), profile, server and configuration; it starts at its first tool call, is shared by the task's sessions, and reports each change of state as an `mcp.server` event (`starting`, `ready`, `failed` with a redacted error and stderr tail, `exited`). Server instructions never reach a prompt, and the client offers no sampling, no elicitation and no roots beyond the workspace.
- **Tool names.** The model calls a server's tool `mcp__<server>__<tool>` (`mcpToolNames`, pi's rule): characters outside `[A-Za-z0-9_]` become `_`, and a name over 64 characters, or one that tools of the server share after that (`a-b` and `a_b`), ends in `_` and 8 hex digits of a SHA-256. Names are given in tool-name order, so the order a server lists its tools in never changes one. They are stable only within a snapshot, where each starts with `mcp__<server>__` and is unique: a new snapshot can rename a tool (`delete_file` gains the suffix once `delete-file` appears). An exact approval rule (`mcp__<server>__<tool>`) must therefore name a tool of its server's pinned snapshot; a profile save refuses one that does not, and the review of a new snapshot lists the tools it renames. `mcp__<server>__*` rules are not affected. No built-in tool starts with `mcp__`, so no server can shadow one.
- **Discovery and snapshots.** Testing a configuration (`POST /api/runtime-profiles/:id/mcp-discoveries`, 202) queues a discovery in the worker, which starts the server (a stdio one in an ephemeral sandbox built from the profile's spec and grants, with no task files) and calls only `initialize` and `tools/list`, never `tools/call`. It stores a tool snapshot: immutable, with each tool's description clipped to 2000 characters and its invisible characters written out, its input schema reduced to an allowlist of keywords (no `pattern`, `format` or remote `$ref`) with every local `$ref` expanded in place, of at most 16 KiB and 12 levels once expanded (where a schema refers to itself it accepts any value, with a warning; a tool whose schema is larger or deeper, or is not an object schema, is left out with a warning; at most 200 tools are read and kept, the first by name), its annotations kept as the server's unverified hints, a hash per tool, the `configHash` of what ran, and warnings. Saving pins a snapshot as `snapshotId`; one discovered for another configuration is refused with 409 `MCP_SNAPSHOT_MISMATCH`. A profile declares at most 64 MCP tools: `declaredMcpTools` lists what it would declare, and a save that would declare more is refused, so no tool is dropped silently.
- **Frozen per session.** A session pins its toolset at its first run. Its MCP declarations come only from the pinned snapshots, after the built-in tools and sorted by name, and stay byte-identical for the session's life: a server's `list_changed` is ignored and drift is reported in `mcp.server`; a profile edit can only take tools away, and a call to a tool taken away is refused with the reason, never undeclared; added or changed tools reach new sessions only.
- **Calls.** An MCP call is reviewed like any tool call. Approval rules name `mcp__<server>__<tool>` or `mcp__<server>__*`. The approval card shows the call's arguments as canonical one-line JSON (keys sorted by code units at every depth). A rule's `match` is looked for in a second text built from the same arguments: their keys and their string and number values, unescaped, in canonical key order, with whitespace collapsed as in every subject, so it sees what the call really holds (`rm -rf /` finds `{"cmd":"rm -rf\n/"}`) in linear time. Arguments that have no canonical form (a cycle, nesting deeper than 64, JSON longer than 1 MiB characters, or a value JSON cannot hold) fail closed: every rule for the tool holds the call, whatever its `match`, and the card says why. Its activity summary is `<server>/<tool>` and that JSON, redacted, with invisible characters written out, at most 300 characters. Results are redacted, then capped at `JJ_OUTPUT_CAP_BYTES` and spilled like other tool output; `isError` makes a result a tool error, and a result keeps at most 4 images of at most 1 MiB each, in PNG, JPEG, GIF or WebP with bytes that start as that type does (others, and malformed blocks, become a line saying so). Those first bytes do not prove an image decodes: a provider may still refuse one. `timeoutSec` bounds each call and progress from the server renews it. A call cut short by a stop, its deadline, its timeout or a crash is cancelled at the server (`notifications/cancelled`), reports `interrupted: unknown` and is never run again. No MCP call makes a model call.
- **Failures.** A server that has not answered `initialize` within `startupTimeoutSec` is stopped and fails. One that exits fails its calls in flight with its exit code and the redacted end of its stderr (the latest 16 KiB are kept); the next call starts it again, at most 3 starts in 10 minutes, after which calls fail at once with the last error until the window passes. A message from a server over 4 MiB closes its connection; one to it over 4 MiB is not sent. A stdio server that stops reading its input for 30 s is taken as broken and stopped. A call that was waiting for its turn when the connection ended was never sent, and says so.
- **Skills.** A skill is an Agent Skills folder (a `SKILL.md` with `name` and `description`, and the files it uses) kept in the server's library. It is uploaded as data (`PUT /api/skills/:name`, each file's content in base64; no archives), and each upload with other content is a new version, identified by its hash. Paths are relative, without `.` or `..` parts; a skill holds at most 100 files and 1 MiB, its `SKILL.md` at most 64 KiB. A profile grants at most 32 by name, as it grants secrets, and deleting a skill removes its grants in the same transaction. A session pins the versions at its first run, and each run writes them into the workspace under `.jj-bot/skills/` (not `.jj`, which Jujutsu uses), restores any file that was changed, and lists them in the prompt with pi's `formatSkillsForPrompt`, so a profile with skills grants `read` or `bash`. A skill's scripts run only in the sandbox, with bash's rights. Skills in a task's own workspace are not loaded.

## Task templates

A task template is a saved task setup the user starts again with one action: a title, a goal, the coordinator and participants, an optional verification plan and a spend cap (the coordinator's profile's at start, none, or an amount). The contract is in `packages/contracts` (`templates.ts`), the routes under `/api/task-templates`.

- **A start is a manual creation.** Starting a template (`POST /api/task-templates/:id/tasks`) builds the create-task command from the template (`templateTaskCommand`): its fields, the run's instructions appended to the goal under `Instructions for this run:`, and the run's own title and cap when given. It then creates the task through `createTask`, the path `POST /api/tasks` takes, with `templateId` set, so the task, its roster, its goal version 1, its root brief and its cap are what manual creation makes from those fields. A goal the instructions push past the task limit is refused with 422 before anything is written.
- **Checked at every start.** Bots, models and caps are read when a task starts, never trusted from the save. A template's problems are derived on each read: an archived participant (`bot_archived`), a participant whose model cannot run (`model_not_configured`), and a plan on a server that does not enforce plans (`verification_unavailable`). A start with any problem is refused with 409 `TEMPLATE_UNUSABLE`, naming them, before it writes anything, so a template never starts without one of its bots. Spend caps are not problems: a coordinator at its cap is refused with `SPEND_CAP_REACHED` as task creation refuses it. Archiving a bot a template names stays allowed.
- **Saves.** A save is checked like task creation (an unknown or archived bot is `VALIDATION_FAILED`), and a server keeps at most 200 templates (`CONFLICT`). An edit replaces the participants whole and is checked as a whole template. Saving, editing and deleting send the `templates.changed` hint.
- **Attribution, not ownership.** A task keeps its `templateId` as a plain id: deleting a template leaves the tasks started from it, and their `templateId`, unchanged.
- **The user's only.** No agent tool, in a task or in direct chat, lists, saves or starts a template, and a template grants nothing manual creation does not. It carries no files and no runtime profile of its own: its tasks run with their coordinator's profile, as every task does.

"Save as template" in the web app fills the template editor from the task as it is now (its current goal, roster, plan and cap, which reads as the profile's when it equals the cap the coordinator's profile sets now); it needs no route of its own.

## Schedules

A schedule starts a task template on its own, at the times a cron expression names on a time zone's wall clock. The contract is in `packages/contracts`: the records in `schedules.ts`, and the cron grammar, the commands and the evaluation of times in `schedule-rules.ts`, the `@jj/contracts/schedule-rules` entry, which clients load only where they write or preview a schedule. The routes are under `/api/schedules`, the pass in `packages/backend/src/worker/scheduler.ts`. Inbound webhook triggers are not part of it ([#134](https://github.com/LemonPhase/jj-bot/issues/134)); a system holding the API token starts runs with `POST /api/task-templates/:id/tasks`.

- **Times.** Five cron fields (`*`, numbers, ranges, steps after `*` or a range, lists, month and weekday names, weekday 0–7); when both day fields are restricted either matches, as in Vixie cron. A seconds field, macros and `L`, `W`, `#`, `?` are refused. A wall time a daylight-saving change skips fires once, at the end of the gap; one it repeats fires once, at its first occurrence. Instants are UTC, and zone rules come from the runtime's ICU at each computation. The editor previews with the functions the server saves with (`cronProblem`, `nextFires`, `minimumGapMinutes`, `triggerProblem`). The next fire is looked for over 2,928 days, so a schedule on 29 February always finds its next one, across a century year without a leap day too; a schedule with none in them is refused.
- **Minimum interval.** No two consecutive fires may be closer on the wall clock than `JJ_SCHEDULE_MIN_INTERVAL_MINUTES` (default 60), measured over the next 366 days, so at most 20 starts an hour at the default. In real time, a change of offset can bring two runs as close as a minute: `59 * * * *` in London runs at 00:59 and, since 01:59 does not exist that night, at 02:00; in Pacific/Chatham the same expression runs 14 minutes apart. So in the hour of a change a schedule can start once more than the minimum allows; a run that has not finished still makes the next due time skip.
- **Saves.** A save is refused (`VALIDATION_FAILED`) for a bad cron or zone, no fire in the horizon, a gap under the minimum, or a template that is unknown or whose task cap resolves to none; and (`CONFLICT`) past 50 schedules or 20 enabled. Those trigger and template checks run when a save creates a schedule, changes its trigger or template from the stored ones (`sameTrigger`: the same expression and canonical zone is no change), or turns a disabled one on; a save that disables it, or changes only its name, instructions, kept workspaces or chat updates, always applies, even when it repeats the trigger and template unchanged, so a schedule the server would now refuse can still be turned off. The editor sends only the fields that changed, and saves such a change while its preview shows the problem. Every edit computes the next fire from now: nothing missed is started afterwards. A template a schedule starts cannot be deleted (`TEMPLATE_IN_USE`); deleting a schedule leaves its tasks running with their `scheduleId`.
- **The pass.** The worker runs it at start and every 30 s and records `lastPassAt` (instance setting `scheduler.last_pass_at`, on the engine's clock); a draining worker runs none. It takes each due schedule with `FOR UPDATE SKIP LOCKED`, one per transaction, so workers on one database never take the same one or wait on each other. Due times recorded already (an edit on a clock behind the worker's can set one again) are passed over. For the latest due time: older than `JJ_SCHEDULE_GRACE_MINUTES` it is `missed`; with an unfinished task of the schedule (queued, running, waiting or stopping) it is `skipped`; else the template starts through its start path, with the schedule's instructions, as a task with `scheduleId` (`started`), or the start is `refused` with the error's code and details. Earlier due times share one `missed` row with their count. A refusal for a spend cap leaves the schedule enabled. Any other turns it off with a `pausedReason`, which enabling it again clears: `template_unusable` (the template's problems, a cap resolving to none), `interval_too_short` (its times are now under the minimum, which is checked again at every fire) or `no_next_fire` (no next time in the horizon, or a zone the runtime no longer knows). An enabled schedule therefore always has a next fire. The newest 200 fires per schedule are kept.
- **Exactly once.** The task a fire starts and the fire's row, unique on the schedule and the due time, are written in one transaction, so no due time starts two tasks, after a crash or a race included, and a restart makes at most one catch-up run per schedule. Schedules fire only while a worker runs; clients warn when `lastPassAt` is more than 2 minutes old.
- **The task.** A scheduled task is the task a manual start of its template makes, with `scheduleId`. Its coordinator's first input ends with `Started by schedule "<name>" for <time on the schedule's wall clock>; the user may not be watching.` Usage, events and caps are the task's, as for any task; a held call waits for the user, and while it does later due times are skipped (`overlap: skip`): nothing a schedule does answers or bypasses it. With `chatUpdates: attention` (the default) the coordinator's chat is told only what needs the user (a question, an approval, a cap) or a failure; `all` adds completions, as for any task.
- **Workspaces.** A task acquiring a sandbox with a `task` workspace records its driver (`workspace_driver`); an ephemeral workspace records nothing and is never counted or removed. Each pass keeps the workspaces of each schedule's newest `keepWorkspaces` finished tasks (default 10) and removes the older ones through the driver that holds each, while it is available, the task is finished with nothing queued or running, and its sandbox is not held. The removal is claimed on the task under its lock, and recorded (`workspace_removed_at`, `workspace.removed`) only once the driver answers that it removed the workspace; a removal that could not happen releases the claim, and a later pass retries it, so none is lost or recorded falsely. An answer that there was none (`removed: false`, as after an operator cleared it) records nothing, so no continuation is told of a removal, and clears `workspace_driver`, so it is not asked again. Artifacts, transcripts and the task log stay. A continuation while a removal is under way is refused (`CONFLICT`) for that moment; one after it starts on a fresh workspace, and the message that continues the task is preceded by a note saying so. A claim older than 5 minutes was lost by a worker that stopped mid-way: a continuation goes ahead and releases it, and every pass releases it first, whether or not the task's schedule, keep or driver remains.
- **The user's only.** No agent tool, in a task or in direct chat, lists, creates or edits a schedule, so a task cannot schedule more work. A schedule's instructions are the user's own fixed text; nothing from outside reaches them.

## Events and streaming

Persist before publishing. Each task event carries an event id, a per-task sequence allocated in the same transaction as the change it records, task id, optional bot, session and run ids, type, timestamp, causal reference and payload.

An event that changes a task, session, message or artifact record, or records a verification check, carries the whole record after the change. A client therefore keeps a task view current by folding events onto it with the contract's pure `applyTaskEvent`, without refetching: a view at sequence n plus events n+1 to m equals the view at m. Other events are markers (goal changed, reopened, finished) and activity. Clients ignore event types they do not know.

Clients receive two streams:

- **Task stream** (`GET /api/tasks/:taskId/stream`): server-sent events over the task event log, one frame per event with the sequence as its `id`, the event type as its `event` and the event as its `data`. It resumes after `Last-Event-ID` or `?after=`. A task view carries the cursor of the last event it reflects, so a client loads the view and streams from that cursor without gaps. Reconnecting replays from the cursor and never re-runs work. A view holds at most the latest 500 events and drops their output previews; earlier events and full previews come from `GET /api/tasks/:taskId/events?after=`.
- **Workspace stream** (`GET /api/stream`): hints naming what changed — bots, a task, a bot conversation, profiles, secrets, templates, schedules. Hints carry no state and are not resumable; clients refetch what they show on every hint and on every (re)connect.

Messages arrive whole; text is not streamed token by token. While a bot works, clients show a per-bot activity line derived from durable events — the command it is running, the file it is editing, a delegation, or that it is writing a reply — so activity survives reload and reconnect. The derivation is a pure contract function, so clients and the server show the same line. Token streaming, if ever added, travels as ephemeral events outside the durable log. Persisted tool output is capped at 64 KiB (`JJ_OUTPUT_CAP_BYTES` can lower it, never raise it); larger output is stored in full as an artifact and the event keeps a truncated preview with a reference to it. The server's secret values are replaced with `[redacted]` in everything a run persists: events, transcript entries, messages, results, the texts collaboration tools store, errors, spilled output, and the paths and names of file artifacts (whose content type still comes from the real path, and whose content stays as written). The runtime applies the replacement before it caps, clips or spills any text it holds whole (tool output, labels, summaries, grep's long lines), so those cuts never leave part of a secret, and the engine applies it again when it writes. Output cut while it arrives cannot be redacted whole first: the sandbox's `maxOutputBytes` on a command (the driver's own cap and bash's collector), a check's head and rolling tail, and the output of a command a timeout or an abort killed. There the cut edge is redacted as one: on the raw text, the longest piece of a secret the text ends (or, for a rolling tail, starts) with is replaced, a bare secret's of at least 4 characters or a database password's of any length next to the `:` or `@` that frames it in a URL, widened over every whole secret it starts or ends inside, and only the rest is then redacted whole, so a secret that holds another (a credentials file and its key, a URL and its password) leaves no piece either. A text cut at both ends, such as the match a `matches` check quotes, is replaced whole when it lies inside a secret, a database password included, also when a cut through a multi-byte character left replacement characters at its ends. A cut therefore leaves at most three characters of a secret, and nowhere but at the cut. The other way round, a cut can mask up to a secret's length less one of ordinary characters that happen to match a piece of one, again only at the cut. A text cut at both ends that is all a piece of 4 or more characters of the database password is masked too, which a short password makes likely: with the documented default `jj_local`, a `matches` check whose match is `local` or `ocal` quotes `[redacted]`. Only two texts are cut at both ends: the match a `matches` check quotes, and the kept tail of a check command's output that its limit cut and a timeout or abort stopped, where all of that tail would have to be such a piece. A cut entry of find's listing is dropped. Finding the piece at a cut costs at most the total length of the secrets, but widening it costs about the text's length times the secrets' total length, divided by the period with which they repeat in it: linear for ordinary text, while a set of long secrets built to repeat with a short period over a text made of them can make one cut take seconds on a few hundred KiB. Only whoever configures the server's secrets and the store's values can set that up. The secrets are the provider keys of the server's environment, the API token, the master keys of the secrets store and every value the store holds, replaced wherever they appear when at least 16 characters long (a shorter configured one is named in a warning at boot and left alone, since it is too likely to be an ordinary word; the store refuses shorter values), and the database password, replaced only as the password of a URL (`:<password>@`). Every occurrence of every secret is found on the raw text before any is replaced, and occurrences that overlap, of two secrets or of one secret with itself, are replaced by one `[redacted]`, so no secret leaves the end of another that overlaps it. Each run reads the stored values afresh when it starts, the [retired](#secrets-store) ones included, and also redacts the values its sandbox was started with, which a replaced or removed secret leaves behind until the sandbox is released, and those of every other sandbox its worker holds, since on `local` one task can read another's files; the final snapshot of a finished task redacts its sandbox's values too. Only the exact value is replaced: an encoded form, such as a token inside a base64 `Authorization` header, is not recognized. Tools receive what the model wrote; only the stored copies are redacted. An approved call is the exception: it runs with its stored, redacted arguments, which are what the user approved (see [Approvals](#approvals)). Files in the workspace are the user's and are stored unredacted, as is their artifacts' content: on `local`, `env > out.txt` keeps the keys in `out.txt`, and a granted secret written into a file stays there on any driver.

## Context and memory

A session's prompt carries the bot's persona and memory, the goal at the session's goal version, the roster, the shared workspace and, for a delegated session, its brief as the requester wrote it. Its inputs are what its inbox delivers. A delegated session starts on its first input (see [Coordination](#coordination)): an index of the task log so far and the user's messages in full, a handoff note when its bot has reported to the delegating session before, and a pointer to the brief in its prompt, so the brief is not sent twice. That is pushed; the rest of the task's record is pulled with the tools below. The first input is the oldest input in the child's transcript, so compaction may summarise it like any other input; the brief, in the prompt, is never summarised.

Every task session, coordinator and workers alike, can also look up its task's shared record with four read-only tools, and its prompt says when to use them:

- `task_state`: the goal and goal version, the task's status (with its result or error once it has one), its verification plan with each criterion's latest outcome at the current goal version, and each session's id, bot, role, status and the first line of its brief.
- `task_log`: the task log, shown oldest first, filtered by kind and by text (ignoring case), from the oldest or the newest entry and paged with `after`, `before` and `limit`; a page says how many matching entries lie before and after it. Each entry is one index line: its id, its kind, its author (→ recipients, or → everyone for a broadcast) and a clipped preview. An entry's id is the stored task message's id, so it never changes. Its kind is `user` (steering, or a message a bot relayed from the user's direct chat), `brief` (an assignment), `report` (a worker's report or failure, or the coordinator's result) or `message` (any other message, the coordinator's replies to the user included).
- `read_entry`: one entry in full, by id.
- `read_report`: a session's brief and its report (or result, or failure) in full, by session id, or by bot name for each of that bot's sessions on the task.

The invariants:

- **Own task only.** The tools read only the caller's task. An id from another task is refused like an unknown one, and a search never matches another task's entries. Listing or searching other tasks is not offered.
- **Never a transcript.** A session's transcript (its reasoning, tool calls and tool output) is private to it: no tool reads another session's transcript, and no model call receives one.
- **Read-only.** The tools change no record and wake no one; like every tool call, each call is recorded as events.
- **Cache-stable.** Their definitions are the same for every session and run; ids and names are checked inside a tool, never listed in its schema.
- **Redacted and capped.** What they read is redacted before any preview clips it, so a cut never leaves part of a secret; the result is capped at `JJ_OUTPUT_CAP_BYTES` and spilled to an artifact like any other tool output.
- **Clean refusals.** An unknown id, another task's id, a NUL character in an argument or a failed read is a tool error the model can act on, never a database message.

An execution session's context is compacted with pi's compaction when it nears its model's context window; direct chat sends a bounded history instead. The [runtime README](../packages/runtime/README.md#context-compaction) has the details; the invariants are:

- **When.** Before a model call whose context passes the window less a reserve (which always leaves the provider room to answer), and once after a provider `context_overflow` or a response the provider cut short for lack of room (its output reached the cap the context left, or it filled the window), which then retries the call. If the context still overflows, the run fails with `context_overflow`. Models with a window under 16384 tokens, or no known window, do not compact, and their overflow errors say so.
- **What.** The bot's own model summarises the older part, keeping decisions, files changed, open delegations, results received and pending work, and folding in any earlier summary. The recent part is kept from a cut point that never separates a tool call from its results. The system prompt is rebuilt every run and is not summarised, so the goal and a delegated session's brief always reach the model as written. A handoff note is an input like the others: once compaction reaches it, the summary is told to keep its session id and the facts the work relies on, and `read_report` still shows that session in full.
- **Persisted.** The compaction is one transcript entry (the summary, how many stored entries before it are kept, the tokens before), written in one transaction after everything it covers. The full transcript stays stored and append-only; a run builds its context as [latest summary] + the kept entries + every entry after it, then repairs crashed tool calls on that view. A crash before the entry is written loses only the summary, and the next run compacts again.
- **Never dropped.** A tool call is summarised or kept together with its results, and one a crash left unanswered is still answered as interrupted, never re-run or lost. Undelivered inbox items stay undelivered (compaction never touches the inbox). The most recent messages up to the cut are kept as they are; when the cut falls inside a turn, the turn's start is summarised with pi's turn-prefix prompt.
- **Accounted.** Each summary call is reported as `model.started` and `model.finished` with its usage, so it has a usage row attributed to its task, session, run and bot.

A bot's memory is one text that the user edits (`PUT /api/bots/:id/memory`). It is added to that bot's own prompts, in task sessions and direct chat, never to a teammate's, and no agent tool writes it. Shared task membership is never authority to read a bot's private conversations.

## Concurrency and recovery

A job lease gives each active run a single owner, and every write-back re-checks ownership. A worker never reclaims a job it is still running: a stall that holds its heartbeats past the lease leaves the run going, and only another worker takes over a lease that expired. Event and conversation sequences are serialized per task and per bot rather than globally, so independent tasks never contend. Side effects of a job that can run again are keyed by its input: a chat reply that runs again after a hand-off or crash creates no second task, relays no message twice and tells a task update once.

A session's pi transcript is persisted as the run proceeds: its inputs before the model call that sees them, an assistant message before its tools run, each tool result as soon as that tool finishes, and a compaction entry once everything it covers is stored. After a crash or restart, the session resumes from what was persisted, in a new run. A session whose last turn had ended finishes that turn as its run would have: the model's answer is persisted, or the engine ended the turn after its calls (it parked the session, or `complete_task` ended the run). Its inbox is taken only for a brief, result or steering, which continues the run as it would have (see [Visibility is separate from activation](#visibility-is-separate-from-activation)); with none, the model is not called, whether or not messages wait, and the session waits, completes or reports as that run would have. A command that was running at the crash is reported to the agent as interrupted with an unknown outcome; it is never silently re-run. A call held for approval is not a crashed call: the session waits for the answer instead of resuming, and an approved call runs at most once (see [Approvals](#approvals)). A session whose workspace did not survive, such as an ephemeral one, is not resumed: it fails visibly. A pi upgrade that changes the transcript format must migrate stored transcripts or refuse to resume them.

A worker that is told to stop drains first. It claims nothing more, keeps its leases and still applies stop requests. A running session stops at its next turn boundary, everything before it persisted, and is handed back there for the next worker to resume from that turn; a run whose model ended its turn with nothing waiting that would continue it ends as it would have. A drain never ends a run any other way: what has not reached a boundary when the drain timeout passes is interrupted exactly as a lost lease interrupts it. It writes nothing more, and once it has stopped its lease is released: expired at once, and at no cost in the job's attempts, so the next worker's claim finds what a dead owner leaves and resumes it as above, at once, however often a drain times out. No new run state is involved, and no run is left half-written. While a process drains, its readiness is not ready.

## Observability

Logs, traces and metrics say what an instance does and why work failed, without becoming a second copy of task history. Setup and the full lists are in [Observability](development.md#observability).

- **Logs** are one JSON object per line by default. A line written while a request, job or run is handled carries the ids it has (`requestId`, `jobId`, `botId`, `taskId`, `sessionId`, `runId`), taken from the asynchronous context, so call sites pass no ids. Once the engine is open, every line goes through its redactor, the one task history uses (provider keys, the API token, the master keys, the database password in URL position, the OTLP exporter's headers, every stored value and the retired ones kept, the values of held sandboxes), rebuilt whenever the engine builds a redactor and after a stored secret changes; an error nothing caught is logged through it before the process exits. Lines from before it opens (a setting that cannot work, a database that cannot be opened) name settings, never values. The one line that carries the generated API token, `Open JJ Bot`, reveals that value and redacts the rest. Request lines carry the path without its query. The engine's lines about runs, replies and calls give ids, names, counts, cost and outcomes, not prompts, briefs, messages, tool arguments, tool output or model text, which stay in the task's records; error messages are logged as raised, redacted.
- **Traces** are OpenTelemetry spans: a session run (`jj.session.run`) or a chat reply (`jj.chat.reply`), each with its model turns (`jj.model.turn`) and tool calls (`jj.tool.call`) as children, and a sandbox start (`jj.sandbox.acquire`) under the run that needed it. Parents are passed explicitly, so no global context manager is required. Attributes are a fixed list of ids, names, token counts, cost and outcomes; never content. The engine depends on `@opentelemetry/api` alone: the SDK and the OTLP exporter are loaded only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, and without it no exporter exists and spans are no-ops. An export is bounded in time and its failure only logged: the collector never holds up or fails a shutdown.
- **Metrics** are one Prometheus registry per engine, served by the API at `/metrics` behind the same guard and token as `/api`. Label values come from bounded sets: job kinds, session roles, outcomes, tool names the run or reply declared (anything a model invents is `other`), catalog models and registered drivers; never a task, session, run, bot or job id. Counters record what happened, so a model call counts whether or not its write-back succeeded. A process reports its own work: with a separate worker, the API's `/metrics` holds the queue but not the worker's runs.
- **Health** is two unauthenticated endpoints that report states, counts and short reasons, never error text, paths, hosts or ids. `/health/live` (and `/health`) is the process alone. `/health/ready` is 200 only when the process is not draining to stop, the database answers, its migrations are at this build's level (none pending, none newer), a worker heartbeat is fresh and a sandbox driver is available; each check that does not answer within 3 s fails. The heartbeat is the embedded loop's last claim pass, or, when the API embeds no worker, a fresh row in `worker_heartbeats`, which every polling worker on PostgreSQL writes with the database clock and removes when it starts to drain or stops.

## Security invariants

- Model keys, provider calls and the worker's environment are never passed into a sandbox. They are out of agent-run code's reach only on drivers that declare filesystem isolation; `local` hides neither the server user's files nor its environment.
- The engine passes into a sandbox only the sandbox secrets its profile grants, by name at acquisition; the driver contract accepts secrets nowhere else. Values entered in settings are stored encrypted with a master key the database never holds, and are never answered back. On a driver without filesystem isolation, commands can read the server's environment, its master key and its database, and so every stored value; settings say so wherever secrets are granted. Model error text is stored with the provider key and key-shaped strings redacted, and the server's secrets are redacted from everything a run persists (see [Events and streaming](#events-and-streaming)), including a value of the store that was replaced or removed less than 90 days ago (the 10 most recent of each name), after every sandbox holding it is released, and the piece of one an output limit cut through, down to 3 characters; workspace files, which a command on `local` can fill with them, are stored as written. Nothing stored quotes a piece of a file cut where redaction cannot see it whole: a `json` check that fails says where the file stops being JSON, by line and column, not the parser's message, which quotes the text around the error. A value refused because it holds or is part of a server secret is refused in the same words whichever secret it is. The refusal still answers one bit, and the rule that a sandbox secret may not be part of a server secret is kept for what it protects: whoever can call `PUT /api/secrets/:name` and already knows 16 characters of a server secret can learn whether a longer candidate is still part of it, one character at a time, and so recover the rest. That is a holder of the API token, or, on a server listening on loopback without `API_TOKEN` (the default for development), any local process or OS user, commands on the `local` driver included, which can read the server's environment anyway. A `docker` sandbox cannot reach the host's loopback, so it reaches the API only where the API listens beyond loopback, and there a token is required.
- A driver refuses any spec it cannot enforce.
- An MCP server's code runs only in a sandbox: a stdio server is a process of the task's sandbox, with bash's rights there. A remote server is reached only by the worker, so its credentials never enter a sandbox, and only a reviewed snapshot's tool definitions reach a model, never a server's instructions.
- Sandboxes never receive the Docker socket, privileged mode or host bind mounts.
- Every tool call is recorded as an event attributed to its task, session and run; a call held for the user's approval is recorded as `approval.requested`, and as tool events only once it runs.
- Log lines are redacted like task history; span attributes and metric labels carry no secret and no task content (see [Observability](#observability)). The health endpoints, which answer without a token, name no secret, path, host or id; `/metrics` requires the token wherever `/api` does.
- The API answers without a token only on loopback. Listening anywhere else it requires a bearer token: the configured one, or one it generates on first boot, keeps in the database and prints only in the line that opens the app. It refuses cross-site requests and non-JSON writes, and without a token it answers only loopback `Host` values, so a web page cannot drive it through the user's browser.
- Remote access takes a token and HTTPS. A reverse proxy or `tailscale serve` on the same host forwards from loopback, so the listener alone cannot tell: the server refuses to start when its settings say something forwards to it (`API_ALLOWED_HOSTS`, or an `API_PUBLIC_URL` beyond loopback) and it would answer without a token, and it refuses a plain-http `API_PUBLIC_URL` beyond loopback, which would carry the token in the clear, unless the operator opts in (`JJ_ALLOW_INSECURE_HTTP`).
- Every answer carries the security headers: a Content-Security-Policy under which pages load and connect to their own origin only, run no script but its files and the web app's one inline script (allowed by its hash; nothing is evaluated from strings), set no `<base>`, embed no plugin, submit no form natively and are framed by nobody (`frame-ancestors 'none'`, and `X-Frame-Options: DENY` for browsers without it), so another site cannot clickjack the app's controls, such as Approve on a held call; `Referrer-Policy: no-referrer`, so an address carrying `?token=` never travels in `Referer`; `X-Content-Type-Options: nosniff`; and HSTS when `API_PUBLIC_URL` is https beyond loopback. The service worker's offline shell keeps the headers it was answered with. An artifact download keeps its own stricter policy (`sandbox`), so agent-written files never run as the app's pages.
