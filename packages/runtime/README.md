# @jj/runtime

The pi agent runtime (`@earendil-works/pi-coding-agent`, `pi-agent-core`, `pi-ai`, pinned at 1.4.0). No database access: the engine supplies inputs and persists what the hooks hand it.

- `ModelRegistry` wraps pi-ai's catalog for the offered providers (each enabled by one API-key variable). `providers()` and `view()` feed `GET /api/models`; `defaultModel()` honours `JJ_DEFAULT_MODEL` when its provider is configured; `resolve(ref | null)` returns the pi model and a key getter. Keys come only from the env the registry was built with and are handed to pi per call. pi's own auth resolution is pointed at that env and never at host credential files.
- `PiSessionExecutor.run(input)` runs one execution session on pi's low-level agent loop over a transcript the engine owns: no pi session files, settings, context files or extensions are loaded.
- `ChatResponder.reply(input)` answers a direct message with the bot's model and the engine's chat tools, at most six model calls, no sandbox.
- `repairTranscript` answers tool calls left without a result by a crash as interrupted with an unknown outcome (nothing is re-run) and puts each call's results back in call order. `serializeEntry` and `parseTranscript` store and load entries (`TRANSCRIPT_FORMAT`: pi messages and compaction entries), refusing shapes they do not recognise. `viewTranscript` builds the model's view of a stored transcript (see [Context compaction](#context-compaction)).
- The scripted test model (`scripted/team`, "Scripted test model") is registered only with `enableScripted`. It is rule-based on the conversation and ignores the free-form system prompt, except that a worker reads its brief from the prompt's last `## Your brief` section (else from its first message); it reads everything else from the tools it is offered and from the engine's result headers. Its role: `create_task`/`send_to_task` mean chat, `complete_task` means coordinator, anything else worker. Whom it delegates to: the enum of `delegate`'s `bot` (the engine omits `delegate` when there is nobody). Active tasks: the enum of `send_to_task`'s `taskId`, with titles in its description as `id: title`. Bots a chat task can include: the item enum of `create_task`'s `participants`. A worker writes the notes file its brief names, then runs once each, with bash, every command its brief quotes after "run" (as in run `sleep 300`), so a goal can give a run a slow or failing step deterministically. A coordinator credits a delegate's outcome only by the first line the engine puts on it, exactly `Result from <bot> (session <id>):` or `Failure from <bot> (session <id>):`; any other message is steering. Like a provider, it refuses a prompt over its context window (four characters a token; 128000 tokens, or `createScriptedProvider({ contextWindow })` in tests) as a context overflow, and caps its output the way pi-ai's providers do (the window less the prompt less 4096, at most 16384), cutting a longer answer with stop reason `length`. Asked for a compaction summary, it records the summarised conversation in a `<scripted-transcript>` block and reads that block back as the start of the conversation, so its rules hold across compactions. It keeps no prompt cache, so its usage is the whole prompt.

## Tools and the sandbox

Every coding tool acts through the run's `Sandbox`, with paths resolved lexically inside the workspace (no `~` expansion, no host filesystem access).

- `read`, `edit` and `write` call `sandbox.fs` directly. pi's versions resolve the agent's path on the host first (read probes name variants with `access()`, edit and write take a `realpath()` lock key), so a host file at the same absolute path could change which sandbox file they touch.
- `bash`, `grep` and `find` run commands through `sandbox.exec`. pi's bash passes the host environment and writes host temp files, pi's grep spawns a host ripgrep, and `find` prunes `node_modules`, `.git`, `dist`, `build` and similar inside the sandbox and scans at most 20,000 entries.
- `ls` is pi's tool on sandbox-backed operations.

bash keeps at most `sandboxLimits.maxOutputBytes` of a command's output and notes when the rest was cut. Tool output over the cap (`JJ_OUTPUT_CAP_BYTES`, at most 64 KiB) is spilled whole through `spillOutput`; the model and the event see its head and tail and the artifact id.

## Run semantics

- Persistence: `onTurnComplete(entries)` receives the run's inputs and injected steering before the model call that sees them, an assistant message that calls tools before those tools run, each tool result as soon as that tool finishes, and a compaction entry alone. Every exit persists what the engine handed over (repairs, inputs, drained inbox items), early exits included. After an abort, calls that never started get a "Not started: the run was stopped." result. System messages are never persisted; the prompt is rebuilt every run. Aborted or failed model responses are not persisted.
- Steering: `drainInbox()` is polled before the first model call and at every turn boundary; texts are injected as user messages through pi's steering hook.
- Budgets: `maxTurns` counts model calls in the run; the deadline aborts what is in flight. Either ends the run with `budget` when the model still wanted to continue.
- Abort: the signal cancels the model call and the running sandbox command; the command reports `interrupted` and the outcome is `aborted`. A sandbox released under the run (`SandboxReleasedError`, or a command interrupted with reason `release`) stops it the same way, with `reason: "sandbox_released"`.
- Timeouts: a model-chosen bash timeout is clamped to the profile's `sandboxLimits.execTimeoutMs` with `resolveExecTimeoutMs`.
- A collaboration tool returning `endRun` (complete_task) ends the run after its tool batch.
- Outcomes: `ended { finalText }`, `idle` (woken with no inputs and an empty inbox: nothing ran), `aborted { reason? }`, `budget { finalText }` and `error { code, error }`. Codes, shared with `ChatReplyError`: `auth`, `rate_limit`, `context_overflow` (pi-ai's `isContextOverflow`), `network`, `provider`, `invalid_request` and `unknown`. Error text has the provider key and anything key-shaped redacted, in outcomes and in `model.finished` events alike.
- Retries: a transient provider failure (429, 5xx, overload, a dropped connection; pi-ai's `isRetryableAssistantError`) is retried up to 3 times with exponential backoff from 1 s, at most 30 s apart, for every provider alike. A context overflow is never retried as transient, whatever its text; compaction handles it. SDK-level retries are off so nothing is retried twice.

## Context compaction

Execution sessions compact their context with pi's compaction (`findCutPoint`, `compact`, `shouldCompact` and `estimateTokens` from `pi-coding-agent`) over the transcript the engine stores; pi's session manager is not used. Direct chat sends a bounded history and never compacts.

- When: before every model call, the run's first included, when the context passes the model's context window less the reserve. The estimate is the latest response's usage plus pi's character estimate of what came after it; usage from a response kept from before the latest compaction is not trusted, and then every message (system prompt and tools included) is estimated. A threshold compaction whose summary call fails is not tried again in that run. A provider `context_overflow` also compacts, regardless of the threshold, and retries the failed call once (the retry does not count against `maxTurns`); so does a response the provider cut short because the context left it no room (pi's recoverable `length` stop, on a request large enough for pi-ai's output cap, the window less the context less 4096, to bite), which is reported as a `context_overflow` error and never persisted, so its truncated tool calls never run. An overflow after that retry, before any response succeeds, or one with nothing older to summarise, ends the run with `context_overflow` and says so.
- What: pi's cut point keeps about `keepRecentTokens` of recent messages (at most half of what the threshold leaves beside the system prompt, tools and latest summary, and scaled by how far the provider's token count runs above pi's estimate) and never cuts at a tool result, so a call and its results stay together; a cut inside a turn summarises the turn's start with pi's turn-prefix prompt. The bot's own model writes the summary in pi's format (goal, constraints, progress, decisions, next steps, critical context, the files read and changed), told to keep the brief, open delegations, received results, steering and whether `complete_task` was called, and folds in the previous summary. The system prompt is rebuilt every run and is never summarised.
- Persisted: one entry, `{ role: "compaction", summary, keptEntries, tokensBefore, readFiles, modifiedFiles, timestamp }`, in one `onTurnComplete` call once everything before it is stored. `keptEntries` counts the stored entries right before it that stay in context. The stored transcript stays append-only and whole.
- Loaded: `viewTranscript` builds the context as [the latest compaction's summary] + its kept entries + every entry after it, skipping older compaction entries; `repairTranscript` then runs on that view, so a crash after a compaction repairs exactly the calls the view holds. A crash between the summary call and its entry's write leaves no entry, and the next run compacts again.
- Never dropped: messages the context holds are persisted before a compaction, so nothing is lost; the inbox is not touched, so undelivered items stay undelivered; the kept part always ends with the latest input or tool results. An answer that is empty, aborted, cut at the length limit or calls a tool is no summary: nothing is persisted.
- Reported: each summary call is a `model.started` and a `model.finished` event (usage included, so the engine stores a usage row), retried like every model call and reported once. Its text starts `Context compaction (about N tokens):` and the summary, or `Context compaction failed (about N tokens):` and the reason when nothing was compacted; a failure also carries a `warning`, which the engine logs.
- Settings: `PiSessionExecutor({ compaction: { enabled, reserveTokens, keepRecentTokens } })`, by default on with pi's 16384 and 20000, fitted to the window: the reserve is at least 8192 (pi-ai's 4096-token output margin plus room to answer) and at most half the window, and the kept part at most half of what is left below the threshold. Compaction is off for a window under 16384 tokens, where it cannot leave room for the prompt, a summary and the kept part, and for a model with no known window; such sessions grow until the window is exceeded.

`configureOutboundProxy(env)` installs undici's `EnvHttpProxyAgent` as the global dispatcher, so the provider SDKs inside pi-ai, which all use Node's global `fetch`, honour `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY`. Processes that call providers run it once at startup.

Tests use pi's faux provider, the scripted model and the `local` sandbox driver; none call a live model. `npm run smoke:runtime` runs one live tool cycle with `JJ_SMOKE_MODEL` (default `openai/gpt-6-luna`).
