# Sandbox drivers

`@jj/sandbox` is the execution isolation boundary. The agent runtime talks only to the `Sandbox` interface; a `SandboxDriver` turns a `SandboxSpec` into a running sandbox. Swapping drivers never reaches orchestration code.

## Contract

- `validateSpec(spec)` parses a spec and **refuses anything the driver cannot honor**: a spec addressed to another driver (`SandboxRequestError`), isolation the driver cannot enforce (`SandboxCapabilityError`), or settings it would ignore, such as an `image` or unknown `driverConfig` keys. Each driver declares `capabilities` — `networkModes` (the `network.mode` values it really enforces), resource limits, filesystem isolation, ports, snapshots, metrics — and `assertSpecSupported` rejects a spec that asks for more. A driver never silently weakens isolation.
- `acquire(request)` returns a sandbox. The worker acquires one per task, shared by all its sessions. A workspace is identified by `spec.workspace` plus `workspaceKey`, so different keys or modes never share files: `task` (the default) persists across releases and is shared by every sandbox with the same key; `ephemeral` is fresh per acquisition and discarded on release; `bot` persists for one bot across tasks and is not used for task execution. No call deletes a `task` or `bot` workspace, so deleting a task leaves its files: the operator clears them. `workspaceKey` must be 1–128 characters of `[A-Za-z0-9_-]` (`assertWorkspaceKey`), in every mode, and is compared case-sensitively. On a case-insensitive filesystem `local` may alias keys that differ only by case; engine-generated keys are lowercase or fixed-case ids, so this does not arise for them.
- `exec(command, options)` streams output through `onData` and caps captured output at `limits.maxOutputBytes` (`truncated` flags overflow so callers can spill to an artifact). A per-call `timeoutMs` can only shorten `limits.execTimeoutMs` (`resolveExecTimeoutMs`). An already-aborted `signal` means the command never starts.
- `interrupted` is `no`, `yes` or `unknown`. `yes` means the driver verified that none of the command's processes, background descendants included, are still running when `exec` resolves. `unknown` means it could not verify that, so the command's effect may already have happened or still be happening.
- `fs` and `cwd` accept workspace-relative paths, or absolute paths inside the workspace. Containment is checked per call on the real path after following symlinks; anything that escapes throws `SandboxPathError`. It is best effort against concurrent changes: a command inside the sandbox that swaps a directory for a symlink mid-call can redirect that call. An isolating driver resolves paths inside the sandbox, never on the host. `remove` and `move` act on a symlink itself, never its target.
- `release()` stops every process the sandbox started, background ones included (commands still running resolve with `interruptReason: "release"`), then discards an `ephemeral` workspace unless `persist` is set. It is idempotent; afterwards `exec` and `fs` reject with `SandboxReleasedError`.
- The sandbox environment is built from scratch. The host or worker environment is never passed in; declared `env` and injected `secrets` are the only additions. Not passing is not hiding: only a driver that declares `filesystemIsolation` keeps the host's files and environment out of reach of agent-run code.

Search (grep and find) runs through `exec` with tools in the sandbox image. It is deliberately not part of `SandboxFs`, so drivers do not each reimplement it.

## Drivers

| Driver   | Isolation                                                                                                                                                  | Use                                          |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `local`  | None. Commands run on the host as the server's user; only the environment is built fresh.                                                                  | Development and trusted single-user machines |
| `docker` | One sibling container per sandbox: non-root, no capabilities, `no-new-privileges`, cgroup limits; named-volume workspace; no Docker socket or host mounts. | Self-hosted installs that run agent code     |

A remote driver, such as one for Daytona, implements the same contract; none ships in this repository.

Workspaces live under the `root` option, else `JJ_SANDBOX_ROOT`, else `<os.tmpdir()>/jj-sandbox`, as `task/<key>`, `bot/<key>` and `ephemeral/<key>-<random>`. The root is fixed, so `task` workspaces survive a server restart; the OS may still clear its temporary directory, so set `JJ_SANDBOX_ROOT` to a durable directory where that matters. The default directory must be owned by the server's user and not be a symlink, or the driver reports unhealthy. Only ephemeral workspaces are deleted, on release; the operator clears the rest of the root.

`local` declares no isolation capabilities. Its only network mode is `open`, so it refuses `none` and `allowlist`; the schema defaults `network.mode` to `none`, so using `local` requires declaring `open` explicitly. It also refuses resource limits, an `image` and any `driverConfig`, and does not run on Windows. It does not pass the server's environment into commands, but hides nothing from them: they can read every file the server's user can (a `.env`, key files, other workspaces) and the server's startup environment through `/proc/$PPID/environ`. Its fs API is contained; its commands are not. Every command gets `GIT_CEILING_DIRECTORIES` set to the root, so git in a workspace without a repository of its own never finds one above the root, even when the operator places the root inside a checkout.

Process cleanup on `local` is best effort without cgroups. Each command runs in its own session and process group and carries a `JJ_SANDBOX_EXEC` marker variable. On interruption the driver sends SIGTERM, waits a grace period, then SIGKILLs whatever is left, whether or not the command's shell has exited. On Linux it also scans `/proc` for processes in the command's session and for marked processes, which catches descendants that left the group, or left the session with `setsid` but kept the marker, and reports `yes` only when a complete scan finds none. A process of the server's user that started after the command and whose environment cannot be read (a non-dumpable one, for example), or a scan that fails, makes the result `unknown`. A descendant that both leaves the session and clears its environment escapes detection. Release stops the groups of finished commands that left processes behind and every marked process. Without `/proc` (macOS) only process groups are stopped, and interrupted commands report `unknown`.

### `docker`

`docker` declares `networkModes: ["none", "allowlist", "open"]`, resource limits and filesystem isolation. `none` leaves the container only a loopback interface; `open` attaches it to the daemon's default bridge; `allowlist` is below. It refuses `resources.diskMb` (named volumes have no size limit) and any `driverConfig`. `cpus`, `memoryMb` (no swap beyond it) and `processes` become the container's cgroup limits; a spec without `processes` still gets a process limit (1024 by default).

Each acquired sandbox is one container created from `spec.image` (default `jj-sandbox:base-1`) through the Docker Engine API. It is never privileged and never receives the Docker socket or a host bind mount. All capabilities are dropped, `no-new-privileges` is set, the container and every command run as uid:gid 1000:1000, and docker-init is PID 1. The workspace is a named volume mounted at `/workspace`, named by mode and key: `<namespace>-task-<key>`, `<namespace>-bot-<key>`, or `<namespace>-ephemeral-<key>-<random>`, where the namespace defaults to `jj-sandbox`. Release force-removes the container, which ends its whole PID namespace, and removes an ephemeral volume. An existing volume is mounted only if it carries the driver's labels for the same mode and key and has no driver options, because a local volume with options can be a host bind mount in disguise. Every container and volume is labelled `jj.sandbox=1`, plus the sandbox, task, session and workspace it belongs to.

Every container also carries `jj.instance`, a random id per server process (`instanceId`). `reapOrphans()` removes the namespace's containers with any other instance id, such as ones a crashed worker left running (egress proxies included), then that instance's allowlist networks; the engine calls it once at worker start. It never removes named volumes: `task` and `bot` workspaces survive, and a crashed worker's ephemeral volumes stay for the operator to delete. Two live workers therefore must not share a namespace on one daemon.

File access goes through exec, never host paths, so the driver works when JJ Bot itself runs in a container with only the Docker socket mounted. A shell helper runs as the sandbox user and resolves every path inside the container with `realpath -m`, so containment is checked on the path the kernel will use, and the fs API can never do more than agent code itself. Agent files never pass through the archive endpoints, which run as root in the daemon. The only archive call is the driver's own: at creation, one empty directory entry gives the volume root to uid 1000, so images without a `/workspace` work too.

No fs call makes the worker buffer an unbounded amount. `fs.read` checks the size inside the container and refuses a file over `maxFileBytes` (32 MiB by default) with `EFBIG` before transferring it. `fs.list` refuses more than `maxListEntries` (20 000 by default) entries with `E2BIG`. Every helper's output is capped at 16 MiB, and the connection is dropped past it. Larger files and listings go through `exec`, whose captured output `limits.maxOutputBytes` caps.

Commands see the image's environment plus spec `env`, secrets and per-call `env`. Secrets are passed to each exec and never stored in the container's configuration. Every command carries a random `JJ_SANDBOX_EXEC` marker. To stop one, the driver scans `/proc` inside the container through a second exec. It sends SIGTERM, waits the grace period, then sends SIGKILL to every process that carries the command's marker or descends from one, which covers `setsid`, `nohup` and double forks. Background processes of other commands are left alone. The driver reports `yes` only when a fresh scan finds none of those processes, and no process that cannot be attributed (no marker, not under a marked process, started after the command) appears in two scans in a row. A descendant that clears its environment and leaves the process tree therefore makes the result `unknown`. Residual limit: a process that copies another command's marker, or keeps forking and exiting faster than a scan can read it, escapes attribution. Commands interrupted by release report `yes`, because the container is gone.

The Engine API address is `DOCKER_HOST` (`unix://` or plain-HTTP `tcp://`), else `/var/run/docker.sock`. That API is root-equivalent on the host, so production installs should put a filtering socket proxy in front of it and point `DOCKER_HOST` at the proxy. Plain `tcp://` is accepted only for a loopback host (`127.0.0.0/8`, `::1`, `localhost`), where such a proxy listens. Any other host, a compose service name included, needs the `allowInsecureTcp` option (`JJ_DOCKER_ALLOW_INSECURE_TCP=true` in the server), because anyone on the network path could drive the daemon. The driver needs only: `/_ping` and `/version`; image inspect and `POST /images/create`; volume create, inspect and remove; container list, create, start, inspect, `PUT …/archive` and remove; network list, create, inspect, connect and remove (allowlist only); and exec create, start and inspect. `DOCKER_TLS_VERIFY` is refused rather than ignored; terminate TLS in such a proxy. Registry credentials are not supported, so private images must be pulled beforehand.

Images need `/bin/sh` and GNU coreutils, findutils and grep (`realpath -m`, `head -z`, `find -printf`, `grep -z`), as in Debian- or Ubuntu-based images; `acquire` checks this and fails with a clear error otherwise. `npm run sandbox:image` builds `jj-sandbox:base-1` from `images/base`: Node 22, git, python3, ripgrep, curl and CA certificates, with user `sandbox` (1000:1000) owning `/workspace`. A missing `jj-sandbox:*` image fails with build instructions; any other missing image is pulled. Bump the tag when the image changes.

What `docker` does not isolate:

- The kernel is shared. A kernel or runtime escape reaches the host; there is no gVisor or user-namespace remapping.
- `open` reaches whatever the default bridge reaches, including host services on the bridge gateway. Never expose a TCP Docker API or socket proxy where a sandbox can reach it.
- Disk use is not limited, and no quota is enforced. A sandbox can fill the daemon's storage through its workspace volume and through the container's writable layer, which stays writable because tools need it. Bounding disk use, for example by giving Docker's data root its own filesystem, is the operator's responsibility.
- Limits apply per sandbox, which a task's sessions share. Commands in one sandbox run as the same user, so they can see and signal each other's processes.

The driver's tests use the image in `JJ_SANDBOX_TEST_IMAGE` when it is set, and fail if that image is missing. Otherwise they use `jj-sandbox:base-1` when it is built, else `node:22-bookworm-slim`. CI builds `jj-sandbox:base-1` and sets the variable to it. The tests skip when no daemon is reachable, and remove every container, volume and network they create. The conformance check that reaches a listed host (`example.com`) needs internet access from containers; `JJ_SANDBOX_TEST_OFFLINE=1` skips that one check, with a note, on a machine where they have none. CI never sets it, so there the check always runs. `src/egress-proxy.test.ts` tests the proxy program itself (entry parsing, matching, address classification, the server and the command the container runs) without a daemon.

#### Network mode `allowlist`

`hosts` entries follow the contract (`NETWORK_HOST_PATTERN`): `host` allows ports 80 and 443, `*.example.com` every subdomain (not `example.com` itself) on those ports, and `host:port` that port only. Entries are lowercased; IPv4 literals are accepted, IPv6 literals are not. A wildcard never covers an IP address: one whose last label is numeric (`*.8.8`, `*.0x8`) is refused, and the proxy never matches a wildcard against an address.

For each allowlist sandbox the driver creates, before the sandbox container:

- an internal bridge network, `<namespace>-net-<sandbox id>`, on its own /28 from the `egressSubnetPool` option (`JJ_DOCKER_EGRESS_SUBNET_POOL` in the server; default `10.213.0.0/16`, room for 4096 networks), never from Docker's default address pools. A /28 that another network on the daemon already holds is skipped; the subnet is free again once the network is removed. The network is `Internal` (no route out), has IPv6 off, and sets `com.docker.network.bridge.inhibit_ipv4`, so the host's side of the bridge gets no address. Docker gives that side the network's IPAM gateway address and, when it honours `inhibit_ipv4`, allocates none; reading the option back would prove nothing, because Docker echoes any option. So the driver reads the network back and refuses allowlist (`SandboxCapabilityError`) unless it is internal, IPv6-free, on the requested /28 and has no gateway.
- an egress proxy container, `<namespace>-egress-<sandbox id>`, from `egressProxyImage` (default `jj-sandbox:base-1`, never the spec's image; it needs only `node` 22 or later, and an image without it fails the acquire with that hint). It runs `src/drivers/egress-proxy.mjs` verbatim (`node --eval`), configured by one environment entry holding the hosts. It is hardened like a sandbox (non-root uid 1000, no capabilities, `no-new-privileges`) and more: read-only root filesystem, 256 MiB, 64 processes, half a CPU, no mounts, no logs, nothing of the host's environment, and `net.ipv4.ip_forward=0`, so it never routes between its networks. It sits on the default bridge, its way out, and on the internal network, and listens only on its internal address (port 3128).

The sandbox container joins only the internal network, so its only neighbour is the proxy, and gets `HTTP_PROXY`, `HTTPS_PROXY`, `http_proxy` and `https_proxy` (`http://<proxy>:3128`), `NO_PROXY`/`no_proxy` (`localhost,127.0.0.1`) and `NODE_USE_ENV_PROXY=1` in its container environment. None of these is secret; secrets still go to each exec only.

Two checks do not rely on the engine version, because older engines leak on internal networks:

- DNS. The sandbox's embedded resolver gets a configured upstream, `198.51.100.53`. Docker resolves a configured upstream from the container's own network namespace, which has no route to it, so no name leaves the sandbox. That holds even on engines whose embedded DNS forwards external names for internal networks from the host's namespace (CVE-2024-29018: before 23.0.11, and 24.0.0 to 25.0.3).
- IPv6. Once the sandbox is running, the driver reads its `/proc/net/if_inet6`. If any interface but `lo` has an IPv6 address, the acquire fails and removes everything. Link-local addresses on IPv4-only interfaces (CVE-2024-32473: 26.0.0 and 26.0.1) would reach host services listening on `[::]`. A kernel without IPv6 has no such file and passes.

The proxy forwards `CONNECT host:port` (any TLS) and absolute-form plain HTTP (`GET http://host/…`, with `Host` replaced by the target's and proxy headers dropped), and only to an allowed host and port. A request body keeps its framing: Node decodes it and sends it on with the same `Content-Length` or as `chunked`, so body bytes can never pass upstream as a second request. Other transfer codings are refused with 501.

The proxy resolves the name itself and refuses the target when any address it resolves to is not public: `0.0.0.0/8`, `10/8`, `100.64/10`, `127/8`, `169.254/16` (cloud metadata included), `172.16/12`, `192.168/16`, the documentation, benchmarking, multicast and reserved ranges, IPv6 outside `2000::/3` (`::1`, `fc00::/7`, `fe80::/10`, NAT64), Teredo, 6to4 and IPv4-mapped forms of those. It then connects to an address it checked, never resolving again. So listing `app`, `postgres`, `host.docker.internal` or a private address never reaches the stack or the Docker host.

A refusal answers 403 (502 when the name does not resolve or the host does not answer) with a one-line reason as the status text and body, such as `JJ Bot egress: example.org is not in this runtime profile's network allowlist` or `JJ Bot egress: postgres resolves to a private address; only public destinations are reachable`. The proxy takes at most 256 connections, 10 s to send request headers and 15 s to connect upstream, and closes a connection that is silent for 5 minutes. Anything it does not understand fails closed: a refused request, a dropped connection, or a proxy that exits, which leaves the sandbox with no network at all.

Release removes the sandbox container, then the proxy, then the network; an acquire that fails midway removes whatever it created. Each resource carries the sandbox's labels, `jj.instance` and `jj.sandbox.role` (`egress-proxy` or `egress-network`), so `reapOrphans()` removes another instance's proxies with its containers, and its networks after them.

Limits of `allowlist`:

- Only proxy-aware HTTP(S) clients work: curl, wget, git over https, pip, npm and Node's `fetch` (with `NODE_USE_ENV_PROXY`; Node 22 prints an experimental warning for it). There is no DNS inside the sandbox, so a client that resolves names itself fails, and ssh, `git://` and every other raw TCP or UDP protocol do not work.
- Only public destinations are reachable; there is no way to allow a private service.
- The Docker host's own public address counts as public. A listed name that resolves to it reaches the host's services that listen on all addresses, so never list names that resolve to the host that runs the sandboxes.
- The proxy filters on the name the client asks for. It does not inspect TLS, so a listed host that fronts other sites (a CDN) may serve requests for them (domain fronting).
- The proxy is the enforcement point. Code that compromised it would get the proxy's network position, which is the default bridge, as in `open`. The proxy holds no secrets, mounts or credentials.
- The subnet pool must be a private range that nothing the sandboxes need overlaps; its addresses are never used on the host itself. A full pool fails the acquire with a message naming the setting.

## Writing a driver

Implement `SandboxDriver`, call `assertSpecSupported` and `assertWorkspaceKey`, then run the shared suite from a test file:

```ts
import { describeSandboxConformance } from "@jj/sandbox/conformance";

describeSandboxConformance("my-driver", () => new MyDriver(), {
  spec: { image: "my-image:latest" },
});
```

Construct the driver inside the factory: the suite plants a host environment canary before calling it, and also checks that `VITEST`, `VITEST_POOL_ID` and `VITEST_WORKER_ID`, which Vitest sets before any import, never reach a command, so a driver that copies `process.env` at module load fails too. The suite asks only for isolation the driver declares, and checks what it declares: a driver listing `none` among `networkModes` must actually block egress; one listing `allowlist` must refuse unlisted hosts, resolve no names for the sandbox and block connections that bypass its proxy, keep the machine running the suite unreachable on every address even when they are listed, and reach a listed public host (`example.com`, over HTTPS and plain HTTP, through `HTTPS_PROXY` or `HTTP_PROXY` when the sandbox has them); and one declaring `filesystemIsolation` must not leak the host environment through `/proc`. The allowlist checks probe with `node` in the sandbox image and fail without it, so a driver that declares `allowlist` is always checked. Drivers whose workspace is a host directory can pass `hostWorkspacePath` so the suite checks that ephemeral release deletes it. A driver that cannot pass must narrow its declared capabilities until it does.
