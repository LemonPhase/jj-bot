# Engine (`@jj/backend`)

The JJ Bot engine: domain services (bots, memory, profiles, tasks, messages, chat, artifacts, views) and the worker (job loop, per-task sandboxes, run lifecycle, wakes, steering, stop, recovery, chat replies) over `@jj/db`. `apps/api` is a thin HTTP and SSE layer over it.

## Wiring

The engine depends on its ports in `src/ports.ts`, never on `@jj/runtime` or a concrete driver. The runtime's classes satisfy them (checked at compile time by `src/runtime-ports.test.ts`). The composition the API and the standalone worker share is `openServices` in `apps/api/src/wiring.ts`; in outline:

```ts
const database = await openDatabase(/* pglite or postgres */);
// Keyring only with JJ_SECRET_KEY; without one the store reads nothing.
const secretStore = new SecretStore({
  db: database.db,
  keyring: createKeyring(masterKey, previousKeys),
});
const models = new ModelRegistry({
  env,
  storedKeys: secretStore,
  enableScripted,
});
const engine = await createEngine({
  db: database,
  drivers: createDriverRegistry([
    { driver: new DockerSandboxDriver({ namespace }), label: "Docker" },
    {
      driver: new LocalSandboxDriver({ root, env: {} }),
      label: "Local (unisolated)",
    },
  ]),
  executor: new PiSessionExecutor({ models, outputCapBytes }),
  chat: new ChatResponder({ models, outputCapBytes }),
  models,
  secretStore,
  secrets: serverSecrets, // env keys, API token, master key: for redaction
  config: configFromEnv(env),
});
await engine.worker.start(); // unless the worker runs in its own process
// On shutdown: await engine.worker.stop(); await database.close();
```

- `createEngine` seeds the default profiles on first boot and returns one method per contract route, each returning that route's response body. Commands are parsed with their contract schemas; refusals throw `DomainError` (`code`, `message`, `details`, `status`).
- The task stream is `engine.tasks.subscribe(taskId, { after, onEvent })`: send each event as an SSE frame (`id` = sequence, `event` = type, `data` = the event) and `close()` on disconnect. The workspace stream is `engine.subscribeHints(handler)`.
- `worker.stop()` hands running work to the next worker; `worker.abandon()` stops like a crash (tests).
- **Observability** (`src/observability/`). `createLogger` writes the JSON (or pretty) lines; `withLogFields` adds ids to every line written inside it, through `AsyncLocalStorage`: the worker scopes each job (`jobId`, `botId`, `taskId`, `sessionId`) and each run (`runId`), the API each request (`requestId`). The engine hands every redactor it builds to `logger.redactWith`, and `logger.reveal` writes the one line that keeps a value (the generated token). `createMetrics` is the engine's own Prometheus registry (`engine.metrics`); pass `metrics` to share one, and `processMetrics` for the process's own. `ActivityTrace` turns a run's or reply's executor events into its span tree and tool-call metrics; the run's span is `rc.activity`, its context the parent of the sandbox start. Pass `tracer` for real spans; the default is the global provider's, a no-op unless one is registered. The worker records its heartbeat row (`recordWorkerHeartbeat`) after a claim pass, at most every `WORKER_HEARTBEAT_MS`, and removes it on `stop()` (not on `abandon()`).
- **Stored secrets** (`src/secrets/`): `keyring.ts` seals and opens values (AES-256-GCM, a key derived from the master key, the row as associated data); `SecretStore` keeps a snapshot of the decrypted rows that `refresh()` reloads (every redactor build calls it, so a standalone worker sees writes the API made) and serves the model registry's `providerKey(id)`. `createEngine` deletes retired values past their 90 days or past a name's 10 most recent (`purgeRetired`), re-seals rows a previous key sealed (`rotate`, retired ones included) and warns, by name, about rows no key opens. Replacing or removing a value retires it in the same transaction (`retired_secrets`, sealed with that table's associated data); `retiredValues()` feeds every redactor, and its provider keys the guards that keep server secrets out of sandboxes; a name keeps one retired row per value, and at most its 10 most recent (`RETIRED_VALUES_PER_NAME`). `services/secrets.ts` holds the write-only routes and `grantedSecrets`, which the worker calls when it starts a task's sandbox: it reads the coordinator profile's grants from the database and fails, naming the secret, when one is missing, unreadable, or holds or is part of a server secret, which it never names. The task sandbox manager keeps the values a sandbox started with (`SandboxHold.secrets`), and each run rebuilds its redactor with them once it holds the sandbox, so a value replaced or removed since stays redacted for as long as the sandbox lives. Every redactor of a worker also covers the values of all the sandboxes it holds (`ctx.heldSecrets`), the final snapshot gets its sandbox's values, and artifact snapshots store file paths and names redacted, which is also how they match the redacted paths of write and edit events for credit.

## Invariants

- **Records travel with events.** Every task or session change goes through `updateTask`/`updateSession`, which emit `task.updated`/`session.updated` with the whole record in the same transaction; activity is stored exactly as `activityFromEvent` folds it. A view plus later events folds into a fresh view.
- **Every write-back is fenced.** A run's writes start with `heartbeat(tx, lease)`; once the lease is lost nothing more is written. Write transactions lock the task row first.
- **No lost wakes.** An inbox item that should wake its session is inserted in the same transaction as its `session.run` enqueue. A running session drains its inbox at each turn boundary, and the end-of-run write-back re-checks the inbox under the task lock and continues the run when a brief, result or steering arrived.
- **Visibility is not activation.** Only briefs, results and steering start or continue a run. A plain `message` is delivered to the addressee's active session without a wake and rides along with its next run; one addressed to a teammate with no active session in the task is refused before anything is posted; a coalesced wake whose input was already taken completes as a no-op even if a message is waiting. `takeInbox` takes the whole inbox in arrival order. Once the turn has ended (`drainInbox(turnEnded)`, a continuation, or a recovery whose transcript's last turn ended, `worker/runs.ts` `turnEnd`: the model's answer, or a turn the engine ended by parking it or with a `complete_task` that ended the run), a run takes its inbox only when a brief, result or steering is in it (messages then ride along), so a message alone never gives the model another turn; a recovery with none finishes the ended turn without a model call. A session that finishes with messages it never read hands them to its parent, quoted, in its result or failure (`worker/unread.ts`): broadcasts are left out, the inbox cap's omitted line is counted as the messages it stands for (which may include broadcasts) with the `task_log` query that finds them, and a clipped message names its entry for `read_entry`.
- **Delegation is a child session.** The brief is the child's `brief` and goes in its system prompt (last, under `## Your brief`), which is rebuilt every run, so context compaction never paraphrases it; the brief inbox item that starts the child, its first input (`worker/first-input.ts`), ends by pointing at it, while the task chat's assignment message carries the brief as written. `childFirstInput` builds that item in the `delegate` transaction before the assignment is posted, and it is stored only in that inbox item: the newest log entries as `indexLine`s and the user's messages quoted in full (both from `listTaskLog`, bounded by the `FIRST_INPUT_*` constants, older ones collapsed into a pointer line), then, when the assignee has already reported to the delegating session, a handoff note (`worker/handoff.ts`): `readLatestReport` picks the bot's latest session under the same parent that completed or failed, and `formatHandoffNote` gives its id (and its goal version when older than the task's) and quotes its brief and report or error, with the `read_report` call that shows them in full. Quotes come from `worker/quote.ts`: every line, whatever break ends it, starts with `> `, and the text is redacted and then clipped to its start and end (`quoteClipped`). Results and failures reach the parent inbox with the first line `Result from <bot> (session <id>):` or `Failure from <bot> (session <id>):`. A parent with open children waits (`waitingFor: delegations`) and holds no job; a coordinator's text at that point is posted as a discussion message. One that only polls is parked (`worker/parking.ts`). `RunHooks.reviewTurn` counts the run's turns whose calls are all `WAITING_TOOLS` and include one of `POLLING_TOOLS` (a turn of `WORKSPACE_READS` alone neither counts nor resets); other calls start the count over, and so does `takeInbox` when it delivers a brief, result or steering. At the `PARK_AFTER_TURNS`th such turn with children open, none of the turn's calls runs (each gets `parkedText`), the run ends `ended` with no text, and the parent waits.
- **Task lookup is read-only and task-scoped.** Every task session gets `task_state`, `task_log`, `read_entry` and `read_report` (`worker/lookup-tools.ts`) over `services/task-log.ts`, which reads one task's state, log and session briefs and reports by task id, and never a transcript. Entry ids are task message ids. An entry's kind comes from one SQL expression over the message's intent, author and relay (steering or relayed from direct chat: `user`; assignment: `brief`; result or system: `report`; otherwise `message`), so filters and labels agree. `listTaskLog` pages from the oldest or the newest entry, after or before an entry id, and counts the matches on either side of the page. The formatters (`indexLine`, `formatTaskLogPage`, `formatEntry`, `formatTaskState`, `formatSessionReport`) are the one text format, and each takes the redactor and redacts before it clips. The tools' definitions are constants; a NUL in an argument or a failed read is a plain refusal; the runtime caps and spills the result like any tool output.
- **Completion.** Only the root coordinator has `complete_task`. It is refused while delegations are open, while a stop is requested, or when the session's goal version is behind the task's. Any input the session takes after recording a completion voids it, across hand-offs and crashes too. A coordinator that ends its turn with nothing open and no completion posts its text and the task waits for the user.
- **Verification gate.** `worker/gate.ts` runs a task's plan when its coordinator's turn ends with a completion request (`sessions.completion_requested`) that no gate has passed: after the executor call and before the run's snapshot and write-back, in the run's sandbox, one criterion at a time (`worker/checks.ts`), each recorded in `verification_checks` with its `verification.checked` event in its own fenced write. A passing attempt is written into the request with the run that ran it (`verification: { attempt, runId }`); another run's verification is stale, so a recovered or later run gates again. Attempt numbers come from the goal version's `verification.started` events, so a cut-off attempt's number is never reused. A failing attempt clears the request and delivers a `result` to the coordinator with a wake, and the run continues past the continuation limit for it. `endTurn` (`worker/outcomes.ts`) completes a task with a plan only after re-reading, in its transaction, that this run's gate passed: every criterion passed at that attempt, and it is the goal version's latest; otherwise the task waits with a system message. Regex matches and JSON Schema validation run in a short-lived worker thread with a 2 s limit from the thread's start, and up to 3 s more for a thread a busy host kept from running (`worker/isolated.ts`), and command output is collected head and tail. `complete_task` refuses once `maxVerificationAttempts` gate runs were made in the run. `services/verification.ts` has the plan's text, the latest checks per goal version and the summary views and `task_state` use.
- **Stop is two-phase.** The request sets `cancelRequestedAt`, cancels queued jobs and tells running runs to abort (a sandbox still starting is aborted too). Nothing launches afterwards: the run-start transaction refuses a session whose task is stopping or finished, or whose parent has finished, and the heartbeat tick stops such runs. When no run is active the task is cancelled with `cancellation.completed` (`stopped` from each run's interrupted command, `neverStarted` for sessions that never ran).
- **One sandbox per task** in a worker, acquired with the coordinator's profile (`workspaceKey = taskId`). It is released when the task finishes (checked against the database, so a task finished on another worker counts) or after `sandboxIdleMs` unused, ephemeral ones included.
- **Ephemeral workspaces** live only in the sandbox that created them. The holding worker records itself on the task (`tasks.sandbox_holder`, a lease refreshed by its heartbeat tick and cleared on release). A session whose task already used one, claimed by another worker, is handed back while that lease is live; otherwise it fails visibly with the reason (released here, or a restart or a stopped holder).
- **Recovery.** A reclaimed job resumes with reason `recovery` from the persisted transcript; the crashed run is closed as failed and its unfinished tools are reported `interrupted: unknown`. Inbox items stay undelivered until the executor persists them, so a crash re-delivers them. Lease-exhausted jobs fail their session visibly.
- **Artifacts.** A run's snapshot stores the files modified since it started, one transaction each, deduplicated by path and SHA-256 per task (at most `maxFilesPerRun` = 50 new artifacts per snapshot, counted after deduplication; `maxFileBytes` = 5 MiB each; 2000 entries listed; `node_modules`, `.git`, `dist`, `build`, `.cache` and `.tmp` skipped). Every run starts with `runs.snapshot_pending` set, and a snapshot that records its files clears it. A run handed back by a graceful stop or cut off by a crash stays pending, so its session's next snapshot reaches back to the earliest pending run's start. When a task finishes, a worker still holding its sandbox takes a final snapshot of the task's remaining pending runs before releasing it; with no sandbox held, nothing is recorded and the runs stay pending. A file is credited to the run whose successful `write`/`edit` call last touched it, among the covered runs and the task's other finished pending runs; other changed files are stored at task level (no session or run), except those a still-running teammate's `write`/`edit` call touched or is still touching (started, its result not yet recorded) that changed no earlier than that run's start less the skew: that run's own scan reaches them, and credits them when it ends. An older file such a call names (it failed, or has not written yet) is stored now, so no file is left to a scan that cannot see it. Credits are read once the scan has read its first file; deciding on a file no one is credited with, the snapshot reads them again, inside the transaction that would store it and under the task lock, if a `write` or `edit` call started since. The scan allows 2 s of clock skew against run start times that other workers may have written, so worker and sandbox clocks must be NTP-synced. Tool output over `JJ_OUTPUT_CAP_BYTES` becomes an `output` artifact and the event keeps a capped preview.
- **Approvals.** `services/approvals.ts` owns the record: `requestApproval` (in the run's write-back, from `RunHooks.reviewToolCall` in `worker/approvals.ts`, which matches the bot's own profile rules and holds one call per session), `decideApproval` (the API, under the task lock), `expireApprovals` (a goal or plan change in `postTaskMessage`: pending approvals and approved calls not yet started), `cancelApprovals` (from `updateSession` whenever a session finishes; a started call that never reported gets an unknown outcome) and the claim and resolution a run's hooks call (`claimApproval` before an approved call runs; `noteResolved` in the `onTurnComplete` transaction that stores the decision's result). A `held` outcome parks the session (`parkHeld`); `startRun` parks a session that still holds one instead of running it (`parkIfHeld`), and an unresolved decision counts as input that starts a run. `continueTask` leaves a coordinator that holds a call waiting, so the message waits for the answer. `settleApprovalWait` at the end of every `finishRun` turns a running task with nothing queued or running and an approval pending into `waiting`.
- **Spend caps.** `services/spend.ts` is the one guard: `spendStop` gives the first cap a model call would exceed (the task's `spend_cap_usd`, the bot's profile `maxUsdPerBotPerDay` over the rolling 24 hours, `JJ_MAX_USD_PER_DAY` over the same), summed in SQL over the priced `usage` rows. A session run asks it before every model call through `RunHooks.admitModelCall` (`worker/run-context.ts`), in a fenced write that records `spend.capped` at a refusal (`noteCapped`: once per cap since the task last reopened) and `spend.threshold` (once per cap value, under the task lock) past 80% of the task's cap; the run's outcome is then `budget`/`spend`, and `finishRun` marks a worker's result as stopped and has a coordinator with nothing open post the cap as a system message and wait for the user. A chat reply asks it too, for the user or for a task update (`worker/chat-reply.ts`), and records each call's usage as it finishes (`onUsage`) and nowhere else, so a reply that fails or whose update is overtaken counts every call once; a refused update reply falls back to the engine's plain message. `delegate` refuses a teammate `spendStop` would stop. `assertWithinCaps` answers SPEND_CAP_REACHED in `continueTask` (every user message, and `send_to_task`), `createTaskTx` (the API and `create_task`) and `sendBotMessage`. A new task takes its cap from the coordinator's profile unless the command gives one; `PATCH /api/tasks/:id` (`updateTaskSettings`) changes it and continues nothing. `services/usage.ts` builds `GET /api/usage` with SQL `filter` aggregates over the last 30 days.
- **Direct chat.** `worker/chat-tools.ts` has the chat's task tools; each covers only the tasks the bot takes part in (`task_participants`). `list_tasks`, `get_task` and `read_task_log` read through `services/task-log.ts` and the lookup tools' page helper, and are marked `readOnly`. Side effects are keyed by the user message being answered, so a reply that runs again after a hand-off or crash repeats none: `create_task` makes at most one task per message (`tasks.created_from_message_id`, unique per bot) and `send_to_task` relays at most once per message and task (`task_messages.relayed_from_message_id`); `send_to_task` continues the task with `continueTask`, and `stop_task` (the coordinator only) uses `requestStopTx`, as `POST /api/tasks/:id/stop` does. `create_task` locks the bot row before counting the tasks it created in the last hour (`JJ_TASKS_PER_BOT_PER_HOUR`). The roster is an enum in `create_task`'s schema; task ids are plain strings checked in each tool.
- **MCP servers** (`services/mcp.ts`, `worker/mcp-discovery.ts`). A profile save checks its merged MCP servers in its transaction, which holds the profile row: each can run here (an MCP client, `spawn` for stdio, `JJ_MCP_REMOTE` for remote), its `secretEnv` granted and `secretHeaders` stored (those rows locked for share), each pinned snapshot this profile's and server's and of the server's `mcpConfigHash`, every exact MCP approval rule naming a pinned tool, and at most 64 declared tools. `startDiscovery` records a queued discovery and its `mcp.discover` job together, then prunes the profile to its newest `MAX_KEPT_DISCOVERIES` and the snapshots it pins or they hold. The job marks it running, acquires an ephemeral sandbox from the profile's spec and grants for a stdio server (released in a `finally`), or reads a remote server's secret headers, and hands the rest to the `McpDiscoverer` port (the runtime's `McpDiscoverer`); it stores the snapshot, validated with `mcpToolSnapshotSchema`, and the outcome in one fenced write, and records nothing for a discovery deleted meanwhile. A graceful stop re-queues it; an exhausted job fails it (`giveUpDiscovery`). `deleteSecret` disables every MCP server that uses the secret.
- **Task updates.** `services/task-updates.ts` records a `chat_task_updates` row, and enqueues the coordinator's `chat.reply`, in the transaction where a task completes or fails (`worker/outcomes.ts`) or starts waiting for the user. A `chat.reply` job (`worker/chat-reply.ts`) answers one input: the user messages no reply has taken up yet (`conversation_messages.handled_at` null), placed last in the history it sends, else the oldest unanswered update, with the read tools only and the update text as a user-role input that is not stored. The job's payload records what it is `answering` before the model call. Answering sets the update's `message_id`, or the user messages' `handled_at`, in the transaction that stores the reply; a failed reply sets `handled_at` too, and a failed update reply posts the engine's fallback message instead. A job whose lease attempts ran out gives up what it was answering (`giveUpChatReply`, from `worker/recovery.ts`): its update gets the fallback without a model call. A job that leaves inputs waiting enqueues the next one. Recording an update closes the task's earlier pending ones (`answered_at` set, no message), and a job closes a waiting update whose task no longer waits instead of telling it (`isOvertaken`). The model's history comes from `worker/chat-history.ts` (card notes, joined turns, a first user turn); `stripCardNotes` runs on every stored reply. `lastReplyError` (`services/chat.ts`) is the failure of the reply to the user's latest message while it stands, else the latest reply's.

## Tests

`npm test` runs the suites on PGlite with the `local` driver and a deterministic `FakeExecutor` (`src/testing/`). `JJ_TEST_DATABASE_URL` switches them to PostgreSQL (each suite creates and drops its own database). The docker variant skips without a reachable daemon.
